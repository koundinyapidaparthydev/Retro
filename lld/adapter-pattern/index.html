Adapter

CORE

The problem they give you

They will not say “Adapter.” They describe this:

Given: Checkout calls stripe.paymentIntents.create. They want PayPal next week. Domain types are Money; the SDK wants cents.

Find: A thin wrapper that satisfies the port you already speak. Translate names, types, and errors. No fee math.

Tiny example: PaypalAdapter implements PaymentMethod. Checkout unchanged. SDK exceptions become domain errors.

Name of the tool

Wrap an existing type so it satisfies the interface your code already speaks — the plug converter of object design.

Why this tool

You rarely own every API.

Approach

  1. Write the target interface the domain already wants.
  2. Hold the vendor/legacy object as a field.
  3. Translate method names, types, and errors at the boundary.

You say this first

I wouldn't name the pattern first. I'd say the problem adapter solves, then the three types. Wrap an existing type so it satisfies the interface your code already speaks — the plug converter of object design.

Shape: Write the target interface the domain already wants.. Don't: You own both interfaces and can change one. When they say 'integrate PayPal too', add PaypalAdapter implementing PaymentMethod. Do not touch Checkout.

More notes if you want them

You rarely own every API. Stripe, a legacy XML service, a third-party maze solver — they do not implement your `PaymentPort`. Adapter is how you keep the domain clean without rewriting the vendor.

Use when: Third-party SDKs, legacy classes, libraries you cannot change.

Skip when: You own both interfaces and can change one.

Trap: Leaky adapter that returns vendor types.
