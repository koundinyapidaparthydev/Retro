The problem they give you

They will not say “Hexagonal architecture.” They describe this:

Given: They want to swap Stripe for PayPal and test booking without a database. The core already imports Express and new Date().

Find: Domain in the middle. Driving adapters call inbound ports. Driven adapters implement outbound ports. Dependencies point in.

Tiny example: Checkout vs PaymentPort and InventoryPort. Fake both in a unit test. Clock is a port for bookings.

Name of the tool

Put the domain in the center, talk to the world through ports, and keep adapters (HTTP, SQL, SMTP) on the outside pointing inward.

Why this tool

Hexagonal (ports and adapters) is how DIP looks on a whiteboard.

Approach

  1. Write the use case against ports only.
  2. Define outbound ports for each IO or volatile detail (time, ids, random).
  3. Implement adapters in other files/packages.

More notes if you want them

Hexagonal (ports and adapters) is how DIP looks on a whiteboard. It is the right story when they ask 'how do you test this' or 'swap Stripe for PayPal'. You can sketch it in 30 seconds and then code only the hexagon plus one adapter.

Use when: Apps with IO, vendors, and tests.

Skip when: Algorithms and in-memory puzzles with no edge.

Trap: Ports named after vendors.
