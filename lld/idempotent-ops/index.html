The problem they give you

They will not say “Idempotent operations.” They describe this:

Given: Mobile retries park() and two tickets issue. Charge $20 twice because the key was amount+time. Cancel-already-cancelled errors.

Find: Same command, same key, one side effect. Store key plus result under the same lock as the mutation.

Tiny example: Wallet.debit(key, money) returns the first receipt. unpark() twice is success. Compare payload; conflict if it differs.

Name of the tool

Repeating the same command with the same key does not repeat the side effect — required once clients retry, double-click, or at-least-once queues exist.

Why this tool

Payments, reservations, and 'create user' get retried.

Approach

  1. Accept an Idempotency-Key or requestId on commands with side effects.
  2. Under the aggregate lock: if key known, return stored result (or conflict).
  3. Else perform the effect, store key → result, return.

You say this first

I wouldn't name the pattern first. I'd say the problem idempotent operations solves, then the three types. Repeating the same command with the same key does not repeat the side effect — required once clients retry, double-click, or at-least-once queues exist.

Shape: Accept an Idempotency-Key or requestId on commands with side effects.. Don't: Pure queries. When they mention retry or double-click, add requestId to the signature immediately.

More notes if you want them

Payments, reservations, and 'create user' get retried. Without idempotency you double-charge and double-book. Interviewers love asking what happens if park() is called twice with the same request id.

Use when: Payments, booking, account creation, email send, anything retried.

Skip when: Pure queries.

Trap: Keys that include time or random values generated server-side after the retry.
