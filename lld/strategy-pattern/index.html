The problem they give you

They will not say “Strategy.” They describe this:

Given: Lot.unpark switches on vehicle type for fees. Elevator.assign is a nest of ifs for peak hour. Checkout will grow UPI next.

Find: One algorithm interface. Context delegates. A factory may pick; the flow does not switch.

Tiny example: Hourly / Daily / Weekend as FeePolicy. Swap SCAN in at 5pm. Adding a coupon is a class.

Name of the tool

Put “the thing that can change” behind a small interface. Swap the brain without rewriting the body.

Why this tool

Strategy is the interview pattern.

Approach

  1. Name the varying algorithm and its inputs/outputs.
  2. Extract an interface.
  3. Inject the strategy into the context constructor or setter.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Weekend price — where do you cut?

You say this first

The algorithm varies, the caller shouldn't. Checkout holds a Payment interface. Card and UPI are two classes. I would not name the pattern first — I name the varying step.

Show two concretes and the inject site. Adding Wallet is a new class. If there is only one algorithm forever, a function is enough — say that.

More notes if you want them

Strategy is the interview pattern. Almost every 'now support another way to X' is a strategy. If you can extract one cleanly, you have demonstrated OCP, DIP, and composition.

Use when: Multiple algorithms for one job: fares, elevator dispatch, payment, compression, sort order, AI difficulty.

Skip when: There is one algorithm and no realistic second — keep a method.

Trap: Strategy that depends on a concrete context type — you have not inverted anything.
