The problem they give you

They will not say “Schema vs objects.” They describe this:

Given: They pasted the bookings table into a class and called it design. Overlap rules have no home because they are not a column. API is Map<String,Object>.

Find: Schema at the wire or store. Objects for operations. Map on purpose.

Tiny example: Reservation computes overlap. The row cannot. URL shortener schema is tiny; uniqueness and expiry live on the object.

Name of the tool

A schema describes the shape of data at rest or on the wire; an object protects behavior and invariants. Do not let JSON or tables become your domain model.

Why this tool

Candidates paste the DB table into a class and call it design.

Approach

  1. Define the wire/storage schema separately from the domain type.
  2. Write a mapper in one place.
  3. Version the schema when you cannot change readers.

You say this first

I wouldn't name the pattern first. I'd say the problem schema vs objects solves, then the three types. A schema describes the shape of data at rest or on the wire; an object protects behavior and invariants. Do not let JSON or tables become your domain model.

Shape: Define the wire/storage schema separately from the domain type.. Don't: In-memory katas with no IO — one object model is enough. If they start with tables, say 'I'll design objects first, then a table that can store them'.

Use when: Any design that persists or speaks HTTP.

Skip when: In-memory katas with no IO — one object model is enough.

Trap: Anemic 'entities' that are Hibernate tables with public fields.
