The problem they give you

They will not say “Immutability.” They describe this:

Given: Money has setAmount. Two threads share a Config map and one reloads keys in place. Undo stores live objects.

Find: Values that never change after construction. Swap a whole snapshot when config reloads.

Tiny example: Money.plus returns new Money. Config is built, then AtomicReference.set. Undo stores copies.

Name of the tool

Prefer objects that do not change after construction so aliases, threads, and undo stacks cannot surprise you.

Approach

  1. Mark fields final / readonly.
  2. If a field is a collection, store an unmodifiable copy.
  3. Implement 'updates' as methods that return a new instance (`withStatus(PAID)`).

More notes if you want them

Mutable shared state is the root of race conditions, dirty caches, and 'I passed this object to two places and one corrupted it.' Immutable values make LLD concurrency and undo designs almost boring — which is what you want.

Use when: Money, IDs, date ranges, addresses, messages, events, config snapshots.

Skip when: Hot inner loops that update large arrays in place — mutate locally, publish an immutable snapshot.

Trap: Storing a caller-owned mutable list — the object is not actually immutable.
