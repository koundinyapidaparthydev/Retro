Definition

Show callers a stable idea — PaymentMethod, PricingRule, ElevatorScheduler — and hide the messy variants behind it.

Why it exists

LLD interviews are variant machines.

Approach

  1. Find the part of the design that will change independently (pricing, unlocking, dispatch, persistence).
  2. Name the capability in domain language, not in framework language.
  3. Write the smallest interface that lets the use case run.

They ask it like this

  • "When would you use Abstraction?"
  • "Our class is growing a switch — what do you do?"
  • "Draw it. Then tell me when you would not."

You say this first

I wouldn't name the pattern first. I'd say the problem abstraction solves, then the three types. Show callers a stable idea — PaymentMethod, PricingRule, ElevatorScheduler — and hide the messy variants behind it.

Shape: Find the part of the design that will change independently (pricing, unlocking, dispatch, persistence).. Don't: There is one implementation and no realistic second one — a single concrete class is clearer. Narrate: 'Checkout should not know how UPI works, only that a PaymentMethod can charge.' Then draw the interface.

More notes if you want them

LLD interviews are variant machines. The first design handles cash; the follow-up adds UPI, then coupons, then surge. Abstraction is how you add those without rewriting the checkout path.

Use when: Two or more algorithms for the same job: pricing, scheduling, matching, notification channels.

Skip when: There is one implementation and no realistic second one — a single concrete class is clearer.

Trap: Interfaces that mirror a concrete class one-to-one — no design, just ceremony.
