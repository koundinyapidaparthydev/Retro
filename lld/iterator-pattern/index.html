The problem they give you

They will not say “Iterator.” They describe this:

Given: Callers take Floor.spots, the live array. You cannot change to a map. Someone parks while a report walks and skips a stall.

Find: A cursor over hidden storage. Say fail-fast vs snapshot if the collection mutates.

Tiny example: lot.spots() yields without exposing Floor[]. File tree DFS iterator. Iterator.remove, not list.remove, mid-walk.

Name of the tool

Walk a collection without exposing its representation — the reason clients can for-each a list, tree, or graph the same way.

Why this tool

If callers know you used a 2D array of spots, you cannot change to a map.

Approach

  1. Hide the storage.
  2. Implement a cursor object with hasNext/next.
  3. Decide fail-fast vs snapshot.

You say this first

I wouldn't name the pattern first. I'd say the problem iterator solves, then the three types. Walk a collection without exposing its representation — the reason clients can for-each a list, tree, or graph the same way.

Shape: Hide the storage. Expose iterator() / [Symbol.iterator] / Iterable.. Don't: A single value — no collection. When you show Floor.spots, say you iterate them, you do not return the list.

More notes if you want them

If callers know you used a 2D array of spots, you cannot change to a map. Iterator (or an Iterable view) is the abstraction. You also need it for Composite trees and for concurrent collections that snapshot.

Use when: Any collection you might reimplement.

Skip when: A single value — no collection.

Trap: Returning the live list from getter.
