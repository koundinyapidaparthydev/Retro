Nouns-to-classes modeling

CORE

Definition

Start from nouns in the prompt, then keep only those that have identity, invariants, or behavior — the rest become fields or values.

Why it exists

This is the standard first modeling move.

Approach

  1. Extract nouns and verbs from the problem statement in two columns.
  2. Tag each noun: entity, value, service/port, field, or drop.
  3. Assign each verb to a type.

You say this first

I wouldn't name the pattern first. I'd say the problem nouns-to-classes modeling solves, then the three types. Start from nouns in the prompt, then keep only those that have identity, invariants, or behavior — the rest become fields or values.

Shape: Extract nouns and verbs from the problem statement in two columns.. Don't: Pure algorithm LLDs (LRU, hashmap internals) — start from operations and complexity, not nouns. Do this out loud: 'Spot is an entity, fee is a value, printer is a port I will skip unless asked.'

More notes if you want them

This is the standard first modeling move. Done naively it produces a class per word (TicketPaper, ParkingFee, Amount). Done well it produces a tight vocabulary you can defend.

Use when: The first five minutes of any object-design interview.

Skip when: Pure algorithm LLDs (LRU, hashmap internals) — start from operations and complexity, not nouns.

Trap: Class `Data`, class `Info`, class `ObjectManager`.
