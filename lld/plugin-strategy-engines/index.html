Plugin and strategy engines

ADV

The problem they give you

They will not say “Plugin and strategy engines.” They describe this:

Given: Checkout edits a switch to add tax, then discount, then a new rail. Third parties cannot ship a rule without a core release.

Find: Closed engine, open registry. Tiny hook interfaces. Config chooses who runs.

Tiny example: validate → quote → authorize → capture. TaxPlugin and DiscountPlugin lists. Add a rail by registering, not editing the engine.

Name of the tool

Make a closed core that runs a pipeline and an open set of plugins/strategies loaded from a registry so features ship without editing the engine.

Why this tool

Pricing engines, lint rules, payment rails, and chess AIs want this shape.

Approach

  1. Define tiny hook interfaces with documented guarantees.
  2. Engine calls hooks; it does not import plugin concretes.
  3. Registry loads and orders plugins.

  • Engine.run → hooks → each plugin. Draw it.

You say this first

I wouldn't name the pattern first. I'd say the problem plugin and strategy engines solves, then the three types. Make a closed core that runs a pipeline and an open set of plugins/strategies loaded from a registry so features ship without editing the engine.

Shape: Define tiny hook interfaces with documented guarantees.. Don't: Two hardcoded strategies — a constructor parameter is enough. For 'support new payment later', a registry of PaymentMethod plus a factory is the engine.

More notes if you want them

Pricing engines, lint rules, payment rails, and chess AIs want this shape. It is OCP at system scale: the engine is closed; the catalog of plugins is open. Interview 'plugin system' designs are this plus a loader.

Use when: Multiple rules/rails/formatters that grow independently.

Skip when: Two hardcoded strategies — a constructor parameter is enough.

Trap: Engine that switches on plugin name anyway.
