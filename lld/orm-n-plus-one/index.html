ORM N+1

ADV

The problem they give you

They will not say “ORM N+1.” They describe this:

Given: listOrders() then each order.getLines() fires a query. GraphQL resolvers do the same. Open-session-in-view hides it until prod.

Find: Name the graph the use case needs. Load it in one or two queries. Lists use a DTO, not a lazy aggregate.

Tiny example: Page of orders, then lines where order_id in (…). Do not lazy-load every seat when listing movies.

Name of the tool

Lazy-loading a collection per parent turns one list call into 1+N queries. Design fetch plans or explicit queries so a page of data is a bounded number of reads.

Why this tool

LLD sometimes includes 'how would you load this'.

Approach

  1. Name the use case and the exact graph it needs.
  2. Write a repository method that loads that graph in 1–2 queries.
  3. Do not walk lazy associations in a loop in a presenter.

You say this first

I wouldn't name the pattern first. I'd say the problem orm n+1 solves, then the three types. Lazy-loading a collection per parent turns one list call into 1+N queries. Design fetch plans or explicit queries so a page of data is a bounded number of reads.

Shape: Name the use case and the exact graph it needs.. Don't: In-memory HashMap designs with no IO — mention it only if they ask about persistence. If they mention JPA/Hibernate, say N+1 and 'I'll add a query that fetches lines in batch'.

More notes if you want them

LLD sometimes includes 'how would you load this'. N+1 is the classic ORM trap: 50 orders × a query per line items. You should know why proxies cause it and how to prevent it without loading the universe.

Use when: Any ORM or lazy graph (also GraphQL resolvers, which have the same shape).

Skip when: In-memory HashMap designs with no IO — mention it only if they ask about persistence.

Trap: Open-session-in-view as a strategy (hides N+1 until prod).
