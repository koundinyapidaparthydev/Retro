Visitor

ADV

The problem they give you

They will not say “Visitor.” They describe this:

Given: File and Folder keep growing methods: size, search, virus-scan, zip. You do not own Node and cannot add export.

Find: Stable structure, growing operations. accept/visit so a new report is a new type — and a new node edits every visitor.

Tiny example: SizeVisitor and SearchVisitor on a file tree. Expression EvalVisitor vs PrintVisitor. Parking lot is not this.

Name of the tool

Add an operation over a stable object structure without changing the element classes — double dispatch for compilers, ASTs, and document trees.

Why this tool

Visitor is the 'I cannot keep adding methods to Node' pattern.

Approach

  1. Give each element accept(Visitor v) { v.visit(this); }.
  2. Visitor interface lists visit methods for every concrete element.
  3. Each operation is a Visitor implementer.

You say this first

I wouldn't name the pattern first. I'd say the problem visitor solves, then the three types. Add an operation over a stable object structure without changing the element classes — double dispatch for compilers, ASTs, and document trees.

Shape: Give each element accept(Visitor v) { v.visit(this); }.. Don't: The hierarchy still grows often. If they ask to add virus-scan and zip-size without editing File/Folder much, Visitor is the textbook move. Composite methods are also acceptable — compare the two.

More notes if you want them

Visitor is the 'I cannot keep adding methods to Node' pattern. It is also easy to misuse on a hierarchy that still changes. Interviews use it for file systems (size, search, virus-scan) and expression trees.

Use when: ASTs, document object models, file trees with many reports, shape hierarchies with export/draw/area as separate ops.

Skip when: The hierarchy still grows often.

Trap: Forgetting a visit method when adding a type.
