Factory vs constructor

NEXT

The problem they give you

They will not say “Factory vs constructor.” They describe this:

Given: Checkout news Car, Bike, Truck, Clock, and a 12-argument Ticket. The same type switch lives in three methods.

Find: Constructor for one simple valid object. Factory when you choose, assemble, or hide collaborators.

Tiny example: new Money(cents, INR). Vehicle.create(type, plate) is the only switch. SearchFilter uses a builder.

Name of the tool

Constructors create one concrete type simply; factories choose, assemble, or hide creation when that job is itself a rule.

Why this tool

New-ing a web of objects inside a use case couples you to every concrete class and hides invariants.

Approach

  1. If creation is `new` plus two arguments and a check, use a constructor (or a named static factory).
  2. If creation needs a switch on type, put that switch in one factory only.
  3. If creation needs collaborators (clock, id, repo), inject those into a factory class.

You say this first

I wouldn't name the pattern first. I'd say the problem factory vs constructor solves, then the three types. Constructors create one concrete type simply; factories choose, assemble, or hide creation when that job is itself a rule.

Shape: If creation is `new` plus two arguments and a check, use a constructor (or a named static factory).. Don't: Abstract Factory for a single product. Put `Vehicle.create(type, plate)` on the board when they list car/bike/truck. That is your closed switch.
