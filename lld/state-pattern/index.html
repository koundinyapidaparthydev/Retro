The problem they give you

They will not say “State.” They describe this:

Given: VendingMachine.select is a 80-line switch. Order allows paid-and-cancelled. Elevator opens the door while moving.

Find: One type per status implements the events. Illegal events fail. Shared data stays on the context.

Tiny example: Idle ignores select. Collecting + select with enough credit goes Dispensing. Draw the machine first.

Name of the tool

Replace a jungle of status flags with objects that each implement behavior for one state and decide the next state.

Why this tool

Vending machines, orders, TCP-like connections, and elevators are state-heavy.

Approach

  1. Draw the state diagram first.
  2. Create a State interface with all events.
  3. Implement one class per state; illegal events throw or no-op by product rule.

You say this first

I wouldn't name the pattern first. I'd say the problem state solves, then the three types. Replace a jungle of status flags with objects that each implement behavior for one state and decide the next state.

Shape: Draw the state diagram first.. Don't: Two statuses with the same methods — an enum is enough. For vending / traffic light / order lifecycle, draw states, then say 'State pattern or a table'. Pick one and implement two transitions.

More notes if you want them

Vending machines, orders, TCP-like connections, and elevators are state-heavy. A switch on enum in every method duplicates transitions. State objects make illegal actions obvious.

Use when: Machines, workflows, connections, game turns, document approval — when each state has different methods that work.

Skip when: Two statuses with the same methods — an enum is enough.

Trap: States that new the next state and also mutate context fields randomly.
