Races, deadlocks, and livelocks

CORE

Definition

A race is uncoordinated access to shared state; a deadlock is a wait cycle; a livelock is motion without progress. Name them and design them out.

Why it exists

Every thread-safety follow-up is one of these.

Approach

  1. List shared mutable locations.
  2. For multi-lock operations, sort locks by a stable key.
  3. Use while (!ready) wait(); never if.

You say this first

I wouldn't name the pattern first. I'd say the problem races, deadlocks, and livelocks solves, then the three types. A race is uncoordinated access to shared state; a deadlock is a wait cycle; a livelock is motion without progress. Name them and design them out.

Shape: List shared mutable locations. Each needs an owner: lock, actor, or atomic.. Don't: Do not add locks 'just in case' on immutable objects. When they say 'make it thread-safe', first name the shared maps. Then pick one lock or one actor per aggregate.

More notes if you want them

Every thread-safety follow-up is one of these. If you can point at the shared data, the lock order, and the retry loop, you look like you have shipped concurrent code.

Use when: Any time you introduce a second thread or a thread pool.

Skip when: Do not add locks 'just in case' on immutable objects.

Trap: Nested locks in opposite order in two methods.
