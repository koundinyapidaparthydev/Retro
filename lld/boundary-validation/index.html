Boundary validation

CORE

The problem they give you

They will not say “Boundary validation.” They describe this:

Given: Controller passes a raw map into ParkingLot. plate == null is checked inside occupy and again in billing. UI-only validation.

Find: Parse and build values at the edge. Domain methods take Email and Money, not strings.

Tiny example: ParkRequest → ParkCommand.of (rejects blank plates) → ParkingService. Auth is a separate 403 step.

Name of the tool

Validate untrusted input at the edge, then build domain values that cannot represent the bad shape — do not re-parse strings in every entity method.

Why this tool

Controllers that pass raw maps into the domain force every class to distrust everyone.

Approach

  1. Parse bytes → DTO with a schema (or manual checks).
  2. Map DTO → command with value objects (this is the second validation).
  3. Call the use case with the command.

More notes if you want them

Controllers that pass raw maps into the domain force every class to distrust everyone. Validate once, construct Email/Money/DateRange, and let the domain assume types are well-formed. Still keep invariants for rules the parser cannot know.

Use when: Every inbound API and message handler.

Skip when: Internal calls that already pass domain types — do not re-validate formats every hop.

Trap: Validating only in the UI.
