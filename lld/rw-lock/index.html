LLD/Concurrency

Read–write lock

NEXT

Definition

Allow many concurrent readers or one writer so read-heavy objects (caches, catalogs) do not serialize on every get.

Why it exists

A single mutex on an LRU cache makes every get wait.

Approach

  1. Document which operations are reads vs writes.
  2. get/contains take readLock; put/evict take writeLock.
  3. Keep sections short; copy what you need, then release.

You say this first

I wouldn't name the pattern first. I'd say the problem read–write lock solves, then the three types. Allow many concurrent readers or one writer so read-heavy objects (caches, catalogs) do not serialize on every get.

Shape: Document which operations are reads vs writes.. Don't: Write-heavy counters — use a mutex or atomic. For a thread-safe cache, mention RW lock or ConcurrentHashMap + synchronized eviction. Do not just say 'synchronize everything'.

More notes if you want them

A single mutex on an LRU cache makes every get wait. If gets dominate and are short, a read-write lock (or a concurrent map plus careful eviction) recovers throughput. Used blindly it starves writers or deadlocks on upgrade.

Use when: Read-mostly in-memory catalogs, configs, session maps.

Skip when: Write-heavy counters — use a mutex or atomic.

Trap: Read-to-write upgrade deadlock.
