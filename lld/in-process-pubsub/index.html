The problem they give you

They will not say “In-process pub/sub.” They describe this:

Given: Modules should react to OrderPlaced without importing each other. A slow email stalls publish. One handler throws and the rest never run.

Find: Broker, typed topics, snapshot the list, isolate errors. Sync vs per-subscriber queues. Unsubscribe token.

Tiny example: Two subscribers; one throws; the other still runs. Async mode with a bounded per-sub queue. No Kafka.

Name of the tool

Publishers send typed events to a Broker; subscribers receive them synchronously or via per-subscriber queues. The broker does not own business rules.

Why this tool

This is Observer with topics, and the kernel of an event bus.

Approach

  1. Immutable events.
  2. Copy the subscriber list before notify.
  3. Catch per-handler errors so one does not kill the rest.

More notes if you want them

This is Observer with topics, and the kernel of an event bus. You need delivery policy (sync/async), unsubscribe, and isolation of a throwing subscriber.

Use when: Decoupling modules in one process: order placed → email, analytics.

Skip when: Two objects — a method call is enough.

Trap: Mutating the subscriber list while iterating.
