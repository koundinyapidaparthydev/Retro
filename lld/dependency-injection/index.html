Dependency injection

CORE

The problem they give you

They will not say “Dependency injection.” They describe this:

Given: Checkout news StripeClient. OrderService news SmtpClient. Twelve services in one constructor. Domain calls Context.getBean.

Find: Pass collaborators in. Composition root knows concretes. A fat constructor is a cohesion smell, not a DI smell.

Tiny example: new ParkingService(lot, clock, payments) in main. Tests are another root. Values like Money are still new-ed per call.

Name of the tool

Pass collaborators in (usually via constructor) instead of constructing or locating them inside the class so the graph is visible and replaceable.

Why this tool

DI is the mechanical habit behind DIP.

Approach

  1. List collaborators.
  2. Type them as interfaces if they are replaceable.
  3. new the concretes only in main/tests.

You say this first

I wouldn't name the pattern first. I'd say the problem dependency injection solves, then the three types. Pass collaborators in (usually via constructor) instead of constructing or locating them inside the class so the graph is visible and replaceable.

Shape: List collaborators. Put them on the constructor.. Don't: Values and entities created per call (`new Money`) — those are not injected services. Write the constructor with three ports. Wire it in a main sketch if they ask 'who news this'.

More notes if you want them

DI is the mechanical habit behind DIP. `new StripeClient()` in Checkout is the bug. A constructor that takes `PaymentPort` is the fix. You do not need a container in an interview; you need a composition root.

Use when: Every service and policy object.

Skip when: Values and entities created per call (`new Money`) — those are not injected services.

Trap: Field injection with no constructor — hard to see and hard to test without a container.
