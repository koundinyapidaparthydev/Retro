LLD/Principles

Separation of concerns

CORE

Definition

Split software along axes that change independently: UI, use cases, domain rules, and infrastructure should not share a file.

Why it exists

SoC is the umbrella over SRP, layers, and hexagonal ports.

Approach

  1. Name the concerns in the problem: rules, state, IO, UI, concurrency.
  2. Assign each to a type or layer.
  3. Keep frameworks in adapters.

You say this first

I wouldn't name the pattern first. I'd say the problem separation of concerns solves, then the three types. Split software along axes that change independently: UI, use cases, domain rules, and infrastructure should not share a file.

Shape: Name the concerns in the problem: rules, state, IO, UI, concurrency.. Don't: A 40-line kata with one class — mention the cut, do not build four packages. Sketch three boxes: API / application / domain+policies, and infra off to the side. That is SoC in 20 seconds.

More notes if you want them

SoC is the umbrella over SRP, layers, and hexagonal ports. If you can change how you store a booking without changing how you price it, you separated concerns. Interview designs that mix System.out, HashMap, and fee math in one class have not.

Use when: Every design that includes both a rule and a store.

Skip when: A 40-line kata with one class — mention the cut, do not build four packages.

Trap: Domain objects importing SQL types.
