The problem they give you

They will not say “Pagination in service APIs.” They describe this:

Given: listBookings() returns the whole table. Page 3 skips rows when inserts land. Sort is by name only and twins swap pages.

Find: limit plus a stable cursor (or honest offset). Clamp size. Do not load then slice.

Tiny example: list(filter, cursor, limit) → items + nextCursor. Opaque cursor. Autocomplete is a tiny page. Chess pieces are a snapshot, not a list API.

Name of the tool

Never return 'all rows' from a growing collection. Use limit + cursor (or page/offset) and a stable sort so callers can walk data safely.

Why this tool

Catalogs, feeds, bookings, and search appear in LLD as 'list X'.

Approach

  1. Add `list(filter, cursor, limit)` to the repository/service.
  2. Clamp limit (default 20, max 100).
  3. Use a unique sort key.

You say this first

I wouldn't name the pattern first. I'd say the problem pagination in service apis solves, then the three types. Never return 'all rows' from a growing collection. Use limit + cursor (or page/offset) and a stable sort so callers can walk data safely.

Shape: Add `list(filter, cursor, limit)` to the repository/service.. Don't: Fixed small sets (a car's 5 seats, a chess board's 32 pieces). If they say 'show all bookings', add pagination in the signature before you implement.

More notes if you want them

Catalogs, feeds, bookings, and search appear in LLD as 'list X'. Unbounded lists blow memory and time. Pagination is part of the signature, not a later optimization.

Use when: Any list that can grow past a few dozen: search, history, inventory admin, bookings.

Skip when: Fixed small sets (a car's 5 seats, a chess board's 32 pieces).

Trap: Returning ArrayList of everything.
