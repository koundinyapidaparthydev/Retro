Double-checked locking

ADV

The problem they give you

They will not say “Double-checked locking.” They describe this:

Given: if (instance == null) { synchronized { if (instance == null) instance = new X(); } } without a safe field. A thread sees a half-built object.

Find: Lazy shared init needs a publication barrier — or a holder / inject and skip the idiom.

Tiny example: volatile instance, second check under the lock. Prefer a static holder. Failed init must not publish a broken instance.

Name of the tool

A lazy-init idiom: check without a lock, then check again under a lock. It is easy to get memory-visibility wrong.

Why this tool

Interviewers use DCL to test whether you understand safe publication, not just synchronized.

Approach

  1. Use a volatile/atomic field for the instance.
  2. First check unsynchronized; return if non-null.
  3. Lock; second check; construct; assign; unlock.

You say this first

I wouldn't name the pattern first. I'd say the problem double-checked locking solves, then the three types. A lazy-init idiom: check without a lock, then check again under a lock. It is easy to get memory-visibility wrong.

Shape: Use a volatile/atomic field for the instance.. Don't: Almost all application code — inject or use eager init. Write volatile, explain why. Then say you would not ship this if a holder class exists.

More notes if you want them

Interviewers use DCL to test whether you understand safe publication, not just synchronized. You should be able to write a correct version and also say 'I would rather use a holder class or an injected singleton'.

Use when: Rare: expensive singleton-like resource you truly want lazy and shared.

Skip when: Almost all application code — inject or use eager init.

Trap: Non-volatile instance field.
