Use-case and state diagrams

NEXT

Definition

Use cases capture who can do what; state diagrams capture which statuses are legal and which events move them.

Why it exists

Many LLD problems are state machines in costume: elevator, traffic light, booking, order, ATM.

Approach

  1. List actors and their goals.
  2. For each long-lived entity, list statuses the problem mentioned.
  3. Draw legal arrows.

You say this first

I wouldn't name the pattern first. I'd say the problem use-case and state diagrams solves, then the three types. Use cases capture who can do what; state diagrams capture which statuses are legal and which events move them.

Shape: List actors and their goals. Cross out goals out of scope.. Don't: CRUD with no lifecycle — a class diagram is enough. For elevator or traffic light, draw the state machine first. Classes fall out of the events.

More notes if you want them

Many LLD problems are state machines in costume: elevator, traffic light, booking, order, ATM. If you only draw classes, you will allow Booked → Parked without paying. State diagrams make illegal transitions visible.

Use when: Bookings, tickets, machines, games, workflows, locks, sessions.

Skip when: CRUD with no lifecycle — a class diagram is enough.

Trap: Boolean pairs (isPaid, isCancelled) that allow paid-and-cancelled-and-pending.
