Program to an interface

CORE

The problem they give you

They will not say “Program to an interface.” They describe this:

Given: Checkout holds StripeClient. NotificationSender holds SmtpClient. Fields are typed ArrayList.

Find: Type collaborators as roles so a fake or a second vendor drops in without editing the policy.

Tiny example: PaymentMethod, OrderRepository, Clock, List. new the concretes in main.

Name of the tool

Write use cases against contracts (ports, roles, collections) so you can swap implementations without editing the policy.

Why this tool

This is the working habit behind DIP, Strategy, and testability.

Approach

  1. For each collaborator, ask if a second implementation is realistic (test fake, second vendor, second algorithm).
  2. If yes, name a role interface and type the field as that role.
  3. Construct the concrete at the edge.

Whiteboard prompts

You say this first

I wouldn't name the pattern first. I'd say the problem program to an interface solves, then the three types. Write use cases against contracts (ports, roles, collections) so you can swap implementations without editing the policy.

Shape: For each collaborator, ask if a second implementation is realistic (test fake, second vendor, second algorithm).. Don't: Values, IDs, and one-off private helpers. Type your fields as interfaces on the diagram. Interviewers read that as seniority.

More notes if you want them

This is the working habit behind DIP, Strategy, and testability. If Checkout holds a `StripeClient`, you cannot fake payments. If it holds a `PaymentMethod`, you can.

Use when: Injected services, policies, repositories, channels, schedulers.

Skip when: Values, IDs, and one-off private helpers.

Trap: IUserService matching UserService 1:1 with no other implementer and no test fake.
