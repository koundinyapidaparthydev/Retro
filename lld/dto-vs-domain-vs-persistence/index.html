The problem they give you

They will not say “DTO vs domain vs persistence.” They describe this:

Given: One User class has JSON annotations, Hibernate annotations, and charge(). Create API requires a persistence id. Hibernate proxies went over the wire.

Find: DTOs travel, domain objects rule, rows store. Map; do not wear three hats unless the app is trivial.

Tiny example: ParkRequest, Ticket, TicketRow. Lists can skip domain. In a 30-minute kata, request + domain is enough.

Name of the tool

Three models, three jobs: DTOs travel, domain objects rule, persistence models store. Map between them; do not make one class wear all three hats unless the app is trivial.

Why this tool

A single `User` class with JSON annotations, Hibernate annotations, and `charge()` is how you couple a rewrite of any layer to all layers.

Approach

  1. For a write use case: DTO → command/values → domain → persist model → store.
  2. For a read: store → persist/query → DTO.
  3. Keep mappers in the adapter layer.
