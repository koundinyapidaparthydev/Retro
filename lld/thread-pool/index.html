The problem they give you

They will not say “Thread pool.” They describe this:

Given: park() starts a thread per car. Under load the machine dies. Cached pools grow without a cap. Rejection is silent discard on bookings.

Find: N workers on a bounded task queue. Submit, reject policy, shutdown. The pool does not fix shared inventory.

Tiny example: CPU-bound ≈ cores. Abort or caller-runs on overflow. Future if the caller needs a receipt.

Name of the tool

Reuse a fixed set of workers to run tasks so you do not create a thread per request and exhaust the machine.

Why this tool

Thread-per-task looks simple and dies under load.

Approach

  1. Choose nThreads and queue capacity.
  2. Workers block on take(); run(); repeat.
  3. submit() either enqueues or applies the rejection policy.

You say this first

I wouldn't name the pattern first. I'd say the problem thread pool solves, then the three types. Reuse a fixed set of workers to run tasks so you do not create a thread per request and exhaust the machine.

Shape: Choose nThreads and queue capacity.. Don't: A single background thread is enough (one logger writer). Never say 'I'll spawn a thread for each park()'. Say 'a pool of workers + queue'.

More notes if you want them

Thread-per-task looks simple and dies under load. A pool caps concurrency, reuses stacks, and gives you a queue for overflow. Connection pools are the same idea for sockets.

Use when: Web request handling, notifications, image processing, any burst of similar tasks.

Skip when: A single background thread is enough (one logger writer).

Trap: Unbounded pool (cached thread pool without a cap) under a flood.
