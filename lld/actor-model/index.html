The problem they give you

They will not say “Actor.” They describe this:

Given: Elevator cars share a mutable stop set with the bank. Lock order across cars is getting scary. Debit is called on account from many threads.

Find: Private state, a mailbox, one message at a time. Others tell(); they do not poke fields.

Tiny example: One actor per car plus a dispatcher. BankAccount handles Debit/Credit. Messages immutable; mailbox bounded.

Name of the tool

Give each actor a mailbox and a single thread of execution so you reason about state without locks on that state.

Why this tool

Actors are the 'do not share memory, share messages' design.

Approach

  1. Define message types (immutable).
  2. Each actor: mailbox + loop: take; match; mutate private state; maybe send.
  3. Expose only tell(message) or ask(message)→Future.

More notes if you want them

Actors are the 'do not share memory, share messages' design. Elevators, players, connection sessions, and aggregates that must serialize updates map well. You trade lock complexity for message-protocol complexity.

Use when: Per-entity serialization: one actor per game table, per websocket, per account.

Skip when: A few fields and one lock would do.

Trap: Sending mutable objects in messages.
