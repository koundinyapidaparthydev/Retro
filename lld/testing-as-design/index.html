Testing as design

CORE

The problem they give you

They will not say “Testing as design.” They describe this:

Given: 'How would you test this?' — they would mock the database, but the DAO is a static singleton. Clock is Date.now() inside the entity.

Find: The first client is a test with fakes. Hidden new, time, and god classes become ports.

Tiny example: ParkingService + in-memory lot + fixed clock. Tests: happy, full, banned, double park, last spot. Do not mock the entity.

Name of the tool

If a use case is hard to test, the design is wrong: missing ports, hidden new, time bombs, or a god class. Let the first test drive the seams.

Why this tool

Interviewers ask 'how would you test this?' to see if you inverted dependencies.

Approach

  1. Write (or name) a test that constructs the use case with fakes.
  2. Any `new ConcreteIo()` inside the core becomes a port.
  3. Any `now()` becomes a Clock.

You say this first

More notes if you want them

Interviewers ask 'how would you test this?' to see if you inverted dependencies. 'I would mock the database' is weak if the database is a static singleton. Testing-as-design means the test is a first-class client of the API.

Use when: Always, as a review question on your own diagram.

Skip when: Do not TDD theater for a 5-minute snippet if they want speed — but still leave seams.

Trap: Tests that only exercise mocks and never assert domain state.
