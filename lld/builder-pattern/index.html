The problem they give you

They will not say “Builder.” They describe this:

Given: HttpRequest has a 12-argument constructor. Two timestamps got swapped. Coffee is new Coffee(true, false, true, 2).

Find: Name each optional part, mutate a builder, freeze a valid product at build().

Tiny example: url required, headers optional. build() rejects inverted dates. Vehicle(plate, type) stays a constructor.

Name of the tool

Assemble a complex object step by step, then freeze a valid result — especially when there are many optional parts or a language-like construction.

Why this tool

Twelve-argument constructors are how you swap two parameters and ship a bug.

Approach

  1. List required vs optional parts of the product.
  2. Give the builder setters/withers for each part.
  3. Hold a Director only if you have named recipes.

You say this first

I wouldn't name the pattern first. I'd say the problem builder solves, then the three types. Assemble a complex object step by step, then freeze a valid result — especially when there are many optional parts or a language-like construction.

Shape: List required vs optional parts of the product.. Don't: Two or three required fields — constructor or static factory. For a query or a pizza/coffee order with add-ons, Builder is the expected pattern.

More notes if you want them

Twelve-argument constructors are how you swap two parameters and ship a bug. Builders name each part, allow fluent setup, and validate once at the end. They also show up in string building, query building, and immutable configs.

Use when: Many optional fields (search criteria, config, notification payload).

Skip when: Two or three required fields — constructor or static factory.

Trap: Reusable builder that forgets to reset and leaks parts into the next product.
