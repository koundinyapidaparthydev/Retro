LLD/Concurrency

Thread-safe cache, counter, and inventory

CORE

Definition

Three standard concurrent objects: a counter (atomics), a cache (map + eviction policy), and inventory (atomic reserve/release with no oversell).

Why it exists

These are the concrete follow-ups after 'make it thread-safe'.

Approach

  1. Counter: atomic increment; read with get(); reset only if product allows.
  2. Cache: map for O(1) lookup; lock around evict/move-to-head; immutable values.
  3. Inventory: lock per SKU or actor; reserve returns a reservation id; confirm/release are explicit.
Time O(1) increment; O(1) cache get/put if structures are hashed; inventory O(1) per SKU lockSpace O(n) entries; plus reservation records if you track holds

You say this first

I wouldn't name the pattern first. I'd say the problem thread-safe cache, counter, and inventory solves, then the three types. Three standard concurrent objects: a counter (atomics), a cache (map + eviction policy), and inventory (atomic reserve/release with no oversell).

Shape: Counter: atomic increment; read with get(); reset only if product allows.. Don't: A single-threaded game loop — atomics add noise. For the last-seat problem, write the atomic reserve method, not a comment that says 'synchronize here'.
