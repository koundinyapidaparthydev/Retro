The problem they give you

They will not say “Notification dispatcher.” They describe this:

Given: OrderService talks SMTP and checkout dies when mail is down. Users who opted out of SMS still get texts. Retries loop forever.

Find: Dispatcher, channel adapters, preferences, bounded queue, idempotent send per notification+channel.

Tiny example: Email + SMS; user disables SMS. Fake failing channel retries then dead-letters. Add Push as a class.

Name of the tool

A Dispatcher takes a Notification and fans it to Channels (email, SMS, push) via a queue and retries. Templates and user preferences are strategies, not if-else in the core.

Why this tool

This is Observer + Strategy + producer-consumer in one useful service.

Approach

  1. Channel interface + adapters.
  2. Preferences filter.
  3. Bounded queue + workers.

More notes if you want them

This is Observer + Strategy + producer-consumer in one useful service. Almost every larger design grows a notifier — design it once as a port plus this engine.

Use when: Any product that emails/SMS/pushes; as a shared subsystem.

Skip when: A single System.out in a kata — a NullNotifier or one Channel is enough.

Trap: SMTP exceptions crashing checkout.
