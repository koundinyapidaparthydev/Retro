The problem they give you

They will not say “Fakes vs mocks.” They describe this:

Given: Tests expect charge() once in this order and miss an oversell. The repo mock returns mocks. Nobody implemented the uniqueness the DB has.

Find: A working stand-in that honors the contract. Mock only a tiny vendor. Assert domain outcomes.

Tiny example: InMemoryBookingRepository with the same unique rule. FakePayment declines on a flag. Fake mailbox list vs a mock send().

Name of the tool

A fake is a working stand-in (in-memory repo). A mock is an interaction assertion (expect charge() once). Prefer fakes for design; use mocks sparingly for true neighbors.

Why this tool

Mock-heavy tests lock you to call order and miss invariant bugs.

Approach

  1. For each port, write a fake that honors the contract (including errors).
  2. Drive use cases through fakes; assert domain outcomes.
  3. Mock only when a fake would be a second SDK.

More notes if you want them

Mock-heavy tests lock you to call order and miss invariant bugs. Fakes let you design a real second implementation of a port — which is exactly what DIP asked for. Interview 'how do you test' answers should start with fakes.

Use when: Fakes: repositories, clocks, id generators, feature flags, in-memory queues.

Skip when: Mocks for every domain object.

Trap: Mocks that return mocks.
