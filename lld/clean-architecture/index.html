Clean architecture

ADV

The problem they give you

They will not say “Clean architecture.” They describe this:

Given: They asked for clean architecture. Someone drew four rings, renamed services Interactors, and left JPA on the entities.

Find: Source points inward. Use cases depend on entities and ports they declare. Frameworks are plugins. A test can run the use case with fakes.

Tiny example: Entities + PlaceOrder + controller + repo adapter. No Spring on the use case. Skip InputBoundary theater in 40 minutes.

Name of the tool

A dependency rule: source code points inward toward entities. Use cases wrap entities; interface adapters translate; frameworks are the outermost detail.

Why this tool

Clean architecture is hexagonal with Uncle Bob's concentric names.

Approach

  1. Write entities with invariants.
  2. Write a use case that depends on entity types + ports.
  3. Implement ports in adapters.

You say this first

I wouldn't name the pattern first. I'd say the problem clean architecture solves, then the three types. A dependency rule: source code points inward toward entities. Use cases wrap entities; interface adapters translate; frameworks are the outermost detail.

Shape: Write entities with invariants.. Don't: Drawing all four rings for tic-tac-toe. Say 'dependency rule: inward only' and draw two rings. Then code.

More notes if you want them

Clean architecture is hexagonal with Uncle Bob's concentric names. Interviewers drop the phrase; they want the dependency rule and a use-case layer, not a 20-circle tattoo.

Use when: When they name it, or when the system has real enterprise rules plus IO.

Skip when: Drawing all four rings for tic-tac-toe.

Trap: Entities with JPA annotations 'because clean'.
