Identity vs value objects

The problem they give you

They will not say “Identity vs value objects.” They describe this:

Given: User.equals compares every field, so a changed email drops them from a Set. Money has an id column.

Find: What stays itself when fields change? What is equal when data matches?

Tiny example: Order is an entity by id. Money(100, INR) equals any other 100 INR. Email validates in its constructor.

Name of the tool

Entities are the same thing over time even if their fields change; values are equal when their data is equal and should be interchangeable.

Why this tool

Mixing these up produces broken equals/hashCode, duplicate bookings, and 'two User objects for one person.' DDD language helps, but the interview need…

Approach

  1. For each noun, ask: if I copy all the fields, is it the same thing or a twin?
  2. Give entities an id.
  3. Give values equals/hashCode on all fields.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Mark entities with id and values without on the diagram.
  • Where does email-format validation live?
  • Never put a mutable User in a HashMap key.

You say this first

I wouldn't name the pattern first. I'd say the problem identity vs value objects solves, then the three types. Entities are the same thing over time even if their fields change; values are equal when their data is equal and should be interchangeable.

Shape: For each noun, ask: if I copy all the fields, is it the same thing or a twin? Same thing → entity. Twin → value.. Don't: Do not invent an id for a price or a color. On the whiteboard, mark entities with id and values without. It makes the class diagram readable.

More notes if you want them

Mixing these up produces broken equals/hashCode, duplicate bookings, and 'two User objects for one person.' DDD language helps, but the interview need is simpler: know what you compare and what you store as a key.

Use when: Anytime you are about to store an email or money as a raw string/int.

Skip when: Do not invent an id for a price or a color.

Trap: equals on all fields for an entity — changing email loses it in a Set.
