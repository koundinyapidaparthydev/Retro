The problem they give you

They will not say “Interfaces vs abstract classes.” They describe this:

Given: The board has both IPaymentMethod and AbstractPayment with no shared steps. Vehicle is an empty abstract class.

Find: Decide capability vs partial implementation. Depend on the contract, not the base.

Tiny example: PaymentMethod is an interface. Add AbstractRetryablePayment only after two gateways share a retry skeleton.

Name of the tool

Use interfaces to name a capability; use abstract classes only when you own a partial implementation that every subtype should share.

Why this tool

Candidates dump both on the whiteboard without a reason.

Approach

  1. Name the capability (`Payable`, `Lockable`, `Schedulable`).
  2. If implementers share no code, stop at the interface.
  3. If they share a skeleton, add an abstract class that implements the interface and marks hooks abstract.

Interfaces vs abstract classes

Name the capability (`Payable`, `Lockable`, `Schedulable`). Write the methods and guarantees.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Should Vehicle be abstract or an interface? Why?
  • A class can implement many roles but extend one parent — what does that imply?
  • Template-method parsers vs strategy AI players — which construct?

You say this first

I wouldn't name the pattern first. I'd say the problem interfaces vs abstract classes solves, then the three types. Use interfaces to name a capability; use abstract classes only when you own a partial implementation that every subtype should share.

Shape: Name the capability (`Payable`, `Lockable`, `Schedulable`). Write the methods and guarantees.. Don't: Abstract class as a bag of static helpers — use a utility or a composed service. Say 'interface first' and only draw an abstract class when you can point at shared steps.

More notes if you want them

Candidates dump both on the whiteboard without a reason. Interviewers want to know why PaymentMethod is an interface and why AbstractOrderParser may be a class — that choice signals whether you understand coupling.

Use when: Interface: any injected collaborator, any test seam, any plugin point.

Skip when: Abstract class as a bag of static helpers — use a utility or a composed service.

Trap: Empty abstract classes that only exist to group types — an interface or a marker is enough.
