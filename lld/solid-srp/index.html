LLD/Principles

SOLID — Single Responsibility Principle

CORE

Definition

A class should have one reason to change. Invoice math should not also send email.

Why it exists

SRP is how you keep a parking-lot design from becoming ParkingLotManager that prices, persists, prints tickets, and sends SMS.

Approach

  1. List the actors or change axes that touch the class.
  2. If you need 'and' to describe the class, draw a cut.
  3. Move each axis behind its own type.

You say this first

I wouldn't name the pattern first. I'd say the problem solid — single responsibility principle solves, then the three types. A class should have one reason to change: one actor, one purpose. Split when two stakeholders would edit the same file for different reasons.

Shape: List the actors or change axes that touch the class.. Don't: Tiny types that would become three one-line classes with no independent meaning. When they add SMS on park, do not open ParkingLot. Add a notifier and call it from the use case.

More notes if you want them

SRP is how you keep a parking-lot design from becoming ParkingLotManager that prices, persists, prints tickets, and sends SMS. Interviewers add a variant; a single-purpose class absorbs it. A god class explodes.

Use when: Any class whose comment is a list of features.

Skip when: Tiny types that would become three one-line classes with no independent meaning.

Trap: Anemic domain + GodService: you moved the blob, you did not apply SRP.
