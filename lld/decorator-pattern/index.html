The problem they give you

They will not say “Decorator.” They describe this:

Given: They asked for retry and metrics on the same gateway. Someone started LoggedRetryUpiGateway extends UpiGateway.

Find: Wrappers that share the interface and stack. Order matters. Core class stays one.

Tiny example: Retry(Log(Real)) logs each attempt. Add metrics by wrapping again at main. Do not edit the gateway.

Name of the tool

Wrap an object with the same interface to add behavior (logging, retry, compression) without subclassing the core.

Why this tool

Decorators are how you mix features: a payment that is logged and retried, a stream that is buffered and compressed.

Approach

  1. Keep a Component interface with the operations you will wrap.
  2. Implement the real core once.
  3. Write one decorator class per extra concern; each holds a Component.

You say this first

I wouldn't name the pattern first. I'd say the problem decorator solves, then the three types. Wrap an object with the same interface to add behavior (logging, retry, compression) without subclassing the core.

Shape: Keep a Component interface with the operations you will wrap.. Don't: You need to add a method that is not on the interface — you cannot decorate what is not there. For 'add retry and metrics', draw two decorators around the gateway. Instant composition-over-inheritance credit.

More notes if you want them

Decorators are how you mix features: a payment that is logged and retried, a stream that is buffered and compressed. Inheritance would need a class per combination; wrapping stacks them.

Use when: Logging, metrics, retry, caching, auth checks, compression, encryption around a port.

Skip when: You need to add a method that is not on the interface — you cannot decorate what is not there.

Trap: Decorator that breaks Liskov (changes return meaning).
