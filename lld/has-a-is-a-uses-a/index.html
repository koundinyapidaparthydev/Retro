Has-a, is-a, and uses-a

CORE

The problem they give you

They will not say “Has-a, is-a, and uses-a.” They describe this:

Given: Library extends ArrayList<Book>. User has-a SmtpClient. Every arrow on the diagram is inheritance.

Find: Pick is-a, has-a, or uses-a, plus multiplicity and who dies with whom.

Tiny example: Lot has floors, floor has spots, spot has optional vehicle. ParkingService uses PaymentPort — Spot does not own it.

Name of the tool

Pick the relationship on purpose: is-a is subtyping, has-a is ownership or composition, uses-a is a short-lived collaboration.

Why this tool

Wrong relationship lines are the most common class-diagram failure.

Approach

  1. For each pair of classes, write one sentence: A is a B / A has a B / A uses a B to do X.
  2. If the sentence needs 'sometimes is-a', it is not is-a — use a role, strategy, or flag.
  3. Decide lifetime: if destroying A must destroy B, compose B.

You say this first

I wouldn't name the pattern first. I'd say the problem has-a, is-a, and uses-a solves, then the three types. Pick the relationship on purpose: is-a is subtyping, has-a is ownership or composition, uses-a is a short-lived collaboration.

More notes if you want them

Wrong relationship lines are the most common class-diagram failure. A Library that 'is-a' List of Books cannot enforce library rules. A User that 'has-a' PaymentGateway forever is equally confused. Name the line before you draw it.

Use when: Every class diagram you draw in an interview.

Skip when: Do not over-annotate every temporary variable as uses-a on the diagram — show types that matter.

Trap: Every relationship drawn as inheritance because the arrow is easy.
