The problem they give you

They will not say “MVC and MVVM.” They describe this:

Given: JButton action runs SQL and prices tickets. The board model imports React. View-Model is a second domain with fee math.

Find: Input in a controller or view-model. Rules in a model or use case. View only renders. Seat map observes bookings.

Tiny example: Tic-tac-toe: Board model, VM with cells[], view binds clicks to place(i). Selected tab is view state, not domain.

Name of the tool

Separate what the user sees from application state: controllers/presenters handle input; views render; models hold rules — MVVM adds a bindable view-model.

Why this tool

UI-heavy LLD (or 'design a client') still shows up.

Approach

  1. Put domain rules in a model or use case, not in click handlers.
  2. Controller/VM: map UI events to use-case calls, map results to view state.
  3. View: render state, no SQL, no fees.

You say this first

I wouldn't name the pattern first. I'd say the problem mvc and mvvm solves, then the three types. Separate what the user sees from application state: controllers/presenters handle input; views render; models hold rules — MVVM adds a bindable view-model.

Shape: Put domain rules in a model or use case, not in click handlers.. Don't: Backend-only LLD — say 'controller is a driving adapter' and move on. If the problem is a UI, draw View / VM-or-Controller / Model. If it is a service, do not force MVC.

More notes if you want them

UI-heavy LLD (or 'design a client') still shows up. If your JButton action performs SQL, you failed MVC. You do not need Android on the board; you need a place for view state vs domain state.

Use when: Desktop/mobile UI, web request/response, dialog-heavy tools.

Skip when: Backend-only LLD — say 'controller is a driving adapter' and move on.

Trap: Business logic in event handlers.
