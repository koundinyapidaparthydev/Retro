Singleton (and its smell)

CORE

The problem they give you

They will not say “Singleton (and its smell).” They describe this:

Given: ParkingLot.getInstance() holds bookings. Tests share a cache and flake. Logger.getInstance() is called from the domain.

Find: If you truly need one instance, say how it is published — and prefer constructing it once in main.

Tiny example: Eager or holder-class logger. Then inject Logger. Lots are not singletons — a mall has many.

Name of the tool

Singleton guarantees one instance and a global access point. That is occasionally correct for a process-wide resource and often a test-hostile hidden dependency.

Why this tool

Interviewers still ask you to write one — and then watch whether you mention the smell.

Approach

  1. Make constructors private.
  2. Choose eager init (simple, thread-safe in Java static holders) or lazy init with a safe publication idiom.
  3. Block clone/serialize paths that could create another instance, if those exist in the language.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Write a safe one-instance logger, then refuse it in the domain.
  • Lazy plus threads — what must be true of the field?
  • Two tests share a singleton cache. How do you unshare?

You say this first

I wouldn't name the pattern first. I'd say the problem singleton (and its smell) solves, then the three types. Singleton guarantees one instance and a global access point. That is occasionally correct for a process-wide resource and often a test-hostile hidden dependency.

Shape: Make constructors private. Hold a static reference.. Don't: Databases, repositories, user sessions, caches that should be scoped or mocked. Write a correct version, then say 'in production I would inject this.' That is the senior move.

More notes if you want them

Interviewers still ask you to write one — and then watch whether you mention the smell. You should know a thread-safe implementation and know when to refuse the pattern in favor of DI.

Use when: A genuine process-wide resource with no meaningful second instance (logging backend, native driver).

Skip when: Databases, repositories, user sessions, caches that should be scoped or mocked.

Trap: Public constructor leftover, so `new` still works.
