The problem they give you

They will not say “Errors vs results.” They describe this:

Given: Lot full throws RuntimeException. Card declined is null. catch (Exception) return null. Charge already happened when you throw.

Find: Expected outcomes in the signature. Bugs throw. Map at the edge. No half-mutated aggregate.

Tiny example: park → Result. Declined is domain; timeout is infra and maybe retry. Partial batch gets its own type.

Name of the tool

Use results (or error codes) for expected outcomes the caller must handle; throw for bugs and truly exceptional breaks of the contract.

Why this tool

Lot full, card declined, and unknown id are not 'exceptions' in the product sense — they are outcomes.

Approach

  1. Classify each failure: expected domain vs infrastructure vs bug.
  2. Expected: Result or a dedicated error type in the signature.
  3. Infrastructure: translate in the adapter; maybe retry; then Result or exception per your app rule.

More notes if you want them

Lot full, card declined, and unknown id are not 'exceptions' in the product sense — they are outcomes. Mixing them with NullPointerException makes APIs unpredictable and try/catch into control flow.

Use when: Any command that can legally fail (full, declined, conflict).

Skip when: Getters that cannot fail — return the value.

Trap: catch (Exception e) { return null; }
