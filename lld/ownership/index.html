The problem they give you

They will not say “Ownership.” They describe this:

Given: Floor and Lot both write freeCount. getSpots() returns the live list. A static Map is the store with no owner.

Find: One writer per mutable thing. Everyone else gets an id, a copy, or a view.

Tiny example: Lot owns spots; the controller never keeps a Spot. Pool owns sockets; clients call release. Cache owns eviction.

Name of the tool

Every piece of mutable state needs one owner who may change it; everyone else holds a copy, an id, or a read view.

Why this tool

Double mutation is the quiet bug: Floor and Lot both decrement freeCount; a cache and a map both hold the same user.

Approach

  1. For each mutable field or collection, write the owner type on the diagram.
  2. If two types both write it, pick one or extract a new owner.
  3. Publish ids or immutable snapshots to non-owners.

You say this first

I wouldn't name the pattern first. I'd say the problem ownership solves, then the three types. Every piece of mutable state needs one owner who may change it; everyone else holds a copy, an id, or a read view.

More notes if you want them

Double mutation is the quiet bug: Floor and Lot both decrement freeCount; a cache and a map both hold the same user. Ownership is how you explain composition, aggregates, and thread safety without waving at 'just synchronize'.

Use when: Composition decisions, caches, pools, graphs of entities.

Skip when: Immutable values — everyone can 'own' a copy.

Trap: Returning the live list of spots.
