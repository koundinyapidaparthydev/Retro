The problem they give you

They will not say “Abstract Factory.” They describe this:

Given: UI builds DarkButton next to LightScrollBar. SQL repo is paired with an in-memory lock by accident.

Find: One factory per family so products that must match are born together.

Tiny example: ThemeFactory.createButton + createMenu. WinFactory vs MacFactory. Client never news a widget.

Name of the tool

Provide an interface for creating a family of related products so the family stays consistent (all dark-theme widgets, all SQL ports, all premium pieces).

Why this tool

When products must match each other, a single Factory Method is not enough — you can mix a DarkButton with a LightScrollBar.

Approach

  1. List the product roles that must stay in one family.
  2. Declare an Abstract Factory with one create method per role.
  3. Implement one concrete factory per family.

You say this first

I wouldn't name the pattern first. I'd say the problem abstract factory solves, then the three types. Provide an interface for creating a family of related products so the family stays consistent (all dark-theme widgets, all SQL ports, all premium pieces).

Shape: List the product roles that must stay in one family.. Don't: One product type — Factory Method or a simple factory. Use this only when they mention a matching set. Otherwise it looks like pattern dumping.

More notes if you want them

When products must match each other, a single Factory Method is not enough — you can mix a DarkButton with a LightScrollBar. Abstract Factory is the 'theme' or 'vendor pack' pattern.

Use when: Multiple matching products: widgets, dialect-specific SQL objects, faction units.

Skip when: One product type — Factory Method or a simple factory.

Trap: Abstract Factory with one method — you overnamed a Factory Method.
