Method signatures

CORE

The problem they give you

They will not say “Method signatures.” They describe this:

Given: park(Object o). process(boolean, boolean, boolean). transfer(from, to, amount) as raw ints so currency swaps.

Find: Domain types, no flag soup, a result that distinguishes lot-full from a bug.

Tiny example: park(Vehicle): Result<Ticket, Full|Banned>. Clock passed in. Split update(user, admin, notify) into named methods.

Name of the tool

A signature is a contract: names, types, preconditions, results, and errors. Design it so the compiler and the caller cannot easily do the wrong thing.

Why this tool

`park(Object o)` and `process(boolean, boolean, boolean)` fail interviews.

Approach

  1. Write the method name as a verb and the args as domain types.
  2. Remove boolean flags by splitting methods or passing an enum/policy.
  3. Choose result vs exception and document it.

You say this first

I wouldn't name the pattern first. I'd say the problem method signatures solves, then the three types. A signature is a contract: names, types, preconditions, results, and errors. Design it so the compiler and the caller cannot easily do the wrong thing.

Shape: Write the method name as a verb and the args as domain types.. Don't: Do not invent a type for every argument in a private helper used once. Write `park(Vehicle v): Result<Ticket, Full|Banned>` on the board. That is a design.

More notes if you want them

`park(Object o)` and `process(boolean, boolean, boolean)` fail interviews. Good signatures use values (Money, SpotId), avoid flag parameters, and make illegal states unrepresentable.

Use when: Every public method, especially service APIs.

Skip when: Do not invent a type for every argument in a private helper used once.

Trap: `Object` / `Map<String,Object>` parameters.
