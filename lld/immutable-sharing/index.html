The problem they give you

They will not say “Immutable sharing.” They describe this:

Given: Fee table is a mutable map. Reload writes keys while park() reads. Events on the queue are reused and mutated.

Find: Publish a finished value. Readers load the reference once. Writers clone, then atomically swap.

Tiny example: New Config built off-thread, AtomicReference.set. Messages immutable. Readers may see version n-1 — say if that is OK.

Name of the tool

Share data that cannot change — or atomically swap a whole snapshot — so readers need no lock.

Why this tool

The easiest correct concurrent design is: mutate on one thread, publish an immutable value, let everyone read it.

Approach

  1. Make the shared type immutable (final fields, copied collections).
  2. Confine mutation to a builder or a single writer.
  3. Publish via atomic swap or a concurrent map put.

Whiteboard prompts

  • Reload fees under the lot without locking readers.
  • Bank balances via stale snapshots — acceptable?

You say this first

I wouldn't name the pattern first. I'd say the problem immutable sharing solves, then the three types. Share data that cannot change — or atomically swap a whole snapshot — so readers need no lock.

Shape: Make the shared type immutable (final fields, copied collections).. Don't: High-frequency in-place updates of a huge array (games, image buffers) — mutate locally, snapshot if needed. For thread-safe config reload: build new Config, atomic swap. Beautiful one-liner design.

More notes if you want them

The easiest correct concurrent design is: mutate on one thread, publish an immutable value, let everyone read it. Config, price lists, routing tables, and game snapshots all work this way.

Use when: Config, feature flags, catalogs, routing, compiled regexes, price cards.

Skip when: High-frequency in-place updates of a huge array (games, image buffers) — mutate locally, snapshot if needed.

Trap: Publishing a 'immutable' object that still has a mutable list field.
