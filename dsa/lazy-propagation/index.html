Lazy Propagation

ADV

The problem they give you

They will not say “Lazy Propagation.” They describe this:

Given: An array. You add (or assign) a value on a whole range, then ask range sums or mins.

Find: Range update and range query, both logarithmic — do not walk every cell.

Tiny example: [1, 2, 3, 4], add 5 to [2, 4] → [1, 7, 8, 9]; sum of [2, 3] = 15.

Name of the tool

Defer a range update on a segment-tree node by storing it in a lazy tag. Push the tag to children only when you must go down. Range update and range query stay O(log n).

Why this tool

Without lazy, a range add is O(n).

Approach

  1. apply(idx, tag): update tree[idx] and compose into lazy[idx].
  2. push(idx): apply(left, lazy[idx]); apply(right, lazy[idx]); lazy[idx]=identity.
  3. rangeUpdate: if no overlap return; if full cover apply and return; else push, recurse, pull (tree[idx]=merge(children)).

Run it in JavaScript

Left is the snippet. Right is the console — one console.log at a time.

pending add sits on a node until you walk through it

const n = 4;
const t = Array(8).fill(0);
const lazy = Array(8).fill(0);

function push(i, l, r) {
  if (!lazy[i]) return;
  t[i] += lazy[i] * (r - l + 1);
  if (l !== r) {
    lazy[i * 2] += lazy[i];
    lazy[i * 2 + 1] += lazy[i];
  }
  console.log("push node", i, "add", lazy[i], "span", r - l + 1);
  lazy[i] = 0;
}

function addRange(i, l, r, ql, qr, v) {
  push(i, l, r);
  if (qr < l || r < ql) return;
  if (ql <= l && r <= qr) {
    lazy[i] += v;
    push(i, l, r);
    return;
  }
  const m = (l + r) >> 1;
  addRange(i * 2, l, m, ql, qr, v);
  addRange(i * 2 + 1, m + 1, r, ql, qr, v);
  t[i] = t[i * 2] + t[i * 2 + 1];
}

addRange(1, 0, n - 1, 1, 3, 5);
console.log("sum all", t[1]);

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Add v to every index in [L, R], then sum a range.
  • Assign every index in [L, R] to v, then ask the min.
  • Why is updating cell by cell too slow here?

You say this first

Defer a range update on a segment-tree node by storing it in a lazy tag. Push the tag to children only when you must go down. Range update and range query stay O(log n). I'd dry-run a tiny case first, then say the invariant and the complexity (O(log n) per range update/query time, O(n) space).

Offer the next notch: push(idx): apply(left, lazy[idx]); apply(right, lazy[idx]); lazy[idx]=identity.. Tradeoff: Point updates only — a plain segment tree or Fenwick. Write apply/push/pull as helpers before the recurse. Interviewers follow that.

More notes if you want them

Without lazy, a range add is O(n). With lazy, Range Update / Range Sum (and range assign) become interview/contest-standard. The discipline is push and pull: before you split a node, apply its tag to the children and clear it; after children update, recompute the node. Mixing tags (add vs assign) needs a clear composition rule.

Use when: Range updates + range queries on a mergeable aggregate.

Skip when: Point updates only — a plain segment tree or Fenwick.

Trap: Forgetting to apply the tag to the node's own sum when setting lazy.
