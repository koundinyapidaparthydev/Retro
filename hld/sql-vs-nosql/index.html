SQL vs NoSQL

CORE

The problem they give you

They will not say “SQL vs NoSQL.” They describe this:

Given: You have joins, money, and a unique email today. Marketing wants a 50 KB flexible profile tomorrow.

Find: Pick the store from the access pattern, not from a slogan.

Tiny example: Checkout 3k writes/s that must not lose a unique constraint; feed 80k reads/s of denormalized cards.

Name of the tool

Pick the store from access patterns and invariants, not from fashion. SQL is relational + a query planner; NoSQL is a family of specialized shapes.

Why this tool

The first data question in every HLD is 'where does this live?' Wrong answer: 'we'll use NoSQL because we scale.' Right answer: transactions and joins…

Approach

  1. List entities, lookups, and invariants (unique, balance, FK-like).
  2. If you need multi-row transactions and rich queries, start SQL.
  3. If you need single-key access at huge scale, start KV/wide-column with a key design.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Postgres or Dynamo for this table — why?
  • What query must stay a transaction?
  • You outgrow one primary. Do you move product or just this table?

You say this first

Pick the store from access patterns and invariants, not from fashion. SQL is relational + a query planner; NoSQL is a family of specialized shapes. I'd only add it if a requirement we wrote down actually needs it. SQL: users, billing, inventory, most CRUD products.

Tradeoff: SQL: integrity and query power, harder write scale and ops of a primary.. Failure mode: One database for OLTP and heavy analytics queries. Say 'Postgres for source of truth; Redis/S3/ES as accessories' as a default.

More notes if you want them

The first data question in every HLD is 'where does this live?' Wrong answer: 'we'll use NoSQL because we scale.' Right answer: transactions and joins vs documents, wide rows, KV, or graphs — and you can use more than one.

Use when: SQL: users, billing, inventory, most CRUD products.

Skip when: Do not pick Cassandra for a reporting app that needs arbitrary filters.

Trap: One database for OLTP and heavy analytics queries.
