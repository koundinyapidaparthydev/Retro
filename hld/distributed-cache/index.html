Design a distributed cache

ADV

The problem they give you

They will not say “Design a distributed cache.” They describe this:

Given: The DB cannot take the read QPS. You want a fleet that looks like one giant Redis.

Find: v1: get/set, TTL, add/remove nodes without dumping the whole working set.

Tiny example: 400k gets/s, 60 nodes, one node dies, a celebrity key is 20% of traffic.

Name of the tool

A Memcached/Redis-cluster-like service: partition keys, replicate if you must, evict, and survive node loss without stampeding origin.

Why this tool

This is the 'build Redis Cluster' interview, cousin of the KV store but with eviction, TTLs, and the contract that data can vanish.

Approach

  1. Client hashes key to a node; Get miss is the caller's problem (aside) unless read-through.
  2. On node add/remove, remap a slice; optionally prefetch.
  3. Evict under memory pressure; expire TTL lazily + sweeper.
