Hedged requests

ADV

The problem they give you

They will not say “Hedged requests.” They describe this:

Given: p99 is awful because 1% of replica reads stall. p50 is fine.

Find: Decide whether a second hedged call is worth the extra load.

Tiny example: Read QPS 30k, one replica hiccups at 2s, hedging would add 10% QPS.

Name of the tool

Send a backup request after a delay (or in parallel) to beat tail latency — and pay extra QPS for it.

Why this tool

Tail latency is often a lucky-slow replica, not a permanently slow cluster.

Approach

  1. Enable only on safe GETs or idempotent RPCs.
  2. Hedge after p95, not at t=0, unless QPS is tiny.
  3. Cancel losers; bound extra outstanding per backend.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • p99 is 2s, p50 is 20ms. What do you try?
  • When is hedging a bad idea?
  • Both hedges hit the same sick shard.

You say this first

Send a backup request after a delay (or in parallel) to beat tail latency — and pay extra QPS for it. I'd only add it if a requirement we wrote down actually needs it. Fan-out reads (search, multi-get) where one slow shard ruins the page.

Tradeoff: Better p99 vs more load and more duplicate work.. Failure mode: Hedging writes. Mention hedging when talking p99 of scatter-gather search.

More notes if you want them

Tail latency is often a lucky-slow replica, not a permanently slow cluster. Hedging (Tail at Scale) is a senior technique. Used blindly on writes it doubles mutations. Used well on idempotent reads it slashes p99.

Use when: Fan-out reads (search, multi-get) where one slow shard ruins the page.

Skip when: POSTs that create orders, unless the same idempotency key is guaranteed.

Trap: Hedging writes.
