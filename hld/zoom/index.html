Design Zoom-like video calls

ADV

The problem they give you

They will not say “Design Zoom-like video calls.” They describe this:

Given: Twelve people join a call and need to hear each other with lip-sync that does not feel broken.

Find: v1: media path, SFU vs MCU, join/leave. Recording is a follow-up.

Tiny example: A 50-person all-hands, one user on 3G, an SFU in one region dies.

Name of the tool

Realtime media: signaling, media servers (SFU), NAT traversal, and a hard latency budget — the tougher cousin of chat.

Why this tool

This is one of the hardest classic HLDs.

Approach

  1. Client signals via WS; ICE finds a path (host/srflx/relay).
  2. Media goes to a regional SFU; SFU forwards based on active speaker and layout.
  3. Simulcast: sender uploads 2–3 layers; SFU picks a layer per receiver.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Design Zoom.
  • Who mixes audio — every client or a server?
  • Someone's uplink dies. Do you freeze, mute, or drop them?

You say this first

I'd treat this as a 45-minute HLD. First I lock v1 of Zoom-like video calls: who uses it, read vs write, latency, what is v2. Realtime media: signaling, media servers (SFU), NAT traversal, and a hard latency budget — the tougher cousin of chat.

Then API, data, one write path and one read path. Deep dive: Client signals via WS; ICE finds a path (host/srflx/relay).. SFU vs MCU: latency/CPU vs simple downlink.

More notes if you want them

This is one of the hardest classic HLDs. You must separate signaling (WS) from media (UDP/WebRTC), explain why mesh dies at ~4 people, and how an SFU scales a 100-person meeting.

Use when: Meetings, telehealth, classrooms, 'design Zoom/Meet.'

Skip when: Do not mesh a 50-person call.

Trap: Putting RTP on a Node HTTP cluster.
