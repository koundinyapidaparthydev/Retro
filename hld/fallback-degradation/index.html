HLD/Reliability

Fallbacks, graceful degradation, and feature flags

CORE

Definition

Serve a worse but useful answer when a dependency fails — stale cache, hide a widget, or flip a flag — instead of a white page.

Why it exists

Availability is often 'degraded mode,' not 'all features up.' Interviewers like a homepage that still renders when recommendations are down.

Approach

  1. Rank features: must, should, nice; only 'must' blocks the page.
  2. On dependency failure, serve stale/empty/default and increment a metric.
  3. Ship risky features behind flags with a kill switch and an owner.

Serve a worse but useful answer when a dependency fails — stale cache, hide a widget, or flip a flag — instead of a white page. I'd only add it if a requirement we wrote down actually needs it. Homepages, feeds, search, recommendations, ads, non-critical personalization.

Tradeoff: Stale fallback: higher availability, consistency/UX risk.. Failure mode: Fallback that leaks cache keys across users. For any social/media design, name one degraded mode (unpersonalized feed, no recs).

More notes if you want them

Availability is often 'degraded mode,' not 'all features up.' Interviewers like a homepage that still renders when recommendations are down. Flags are how you ship and how you turn off a burning feature without a rollback of everything.

Use when: Homepages, feeds, search, recommendations, ads, non-critical personalization.

Skip when: Do not fallback a payment authorization to 'assume paid.'

Trap: Fallback that leaks cache keys across users.
