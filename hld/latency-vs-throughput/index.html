Latency vs throughput

CORE

The problem they give you

They will not say “Latency vs throughput.” They describe this:

Given: Batch ingest wants a million writes a minute. The user tap wants 80ms. Same team, same cluster.

Find: Separate the interactive path from the bulk path so you do not optimize the wrong number.

Tiny example: Interactive p99 80ms at 5k QPS vs a 2M/s pipeline that can wait 30s.

Name of the tool

Latency is how long one request waits. Throughput is how many the system finishes per second. Optimizing one can hurt the other — batching is the usual example.

Why this tool

Users feel latency.

Approach

  1. Break latency into parts: client RTT, LB, app, cache, DB, downstream fan-out.
  2. Measure p50/p95/p99, not averages.
  3. Raise throughput with parallelism, batching, connection pooling, and cheaper work per request (cache, denormalize).

More notes if you want them

Users feel latency. Capacity planning is throughput. If you only quote QPS you hide tail latency; if you only quote p50 you hide that the cluster is already saturated. HLD answers need both, plus percentiles.

Use when: Latency-first: interactive APIs, search-as-you-type, checkout, live video start time.

Skip when: Do not batch user-facing writes just to pump throughput if it adds hundreds of ms.

Trap: Using average latency as the SLO.
