Sharding: range, hash, and directory

CORE
AmazonhotMetahotGoogleoftenHot partition follow-up.

Definition

Split a dataset across nodes by a key — range for scans, hash for evenness, directory for flexibility — and live with cross-shard pain.

Why it exists

Write scale beyond one primary is almost always sharding.

Approach

  1. Pick a shard key that matches the hottest query and spreads writes.
  2. Keep transactions and unique constraints inside one shard when you can.
  3. Plan reshard: consistent hashing, range splits, or directory moves.

You say this first

Split a dataset across nodes by a key — range for scans, hash for evenness, directory for flexibility — and live with cross-shard pain. I'd only add it if a requirement we wrote down actually needs it. When one primary cannot take writes or the working set.

Tradeoff: Range: great scans, hot head/tail.. Failure mode: Global unique indexes that secretly need a gather. Propose a key, then attack it with a celebrity/whale/time hotspot and fix it.

More notes if you want them

Write scale beyond one primary is almost always sharding. The key you pick is the design. Interviews fail people who shard 'by id' without saying which id, and who forget scatter-gather and resharding.

Use when: When one primary cannot take writes or the working set.

Skip when: Do not shard a 20 GB database to look scalable.

Trap: Global unique indexes that secretly need a gather.
