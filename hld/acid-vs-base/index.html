ACID vs BASE

CORE

The problem they give you

They will not say “ACID vs BASE.” They describe this:

Given: The ledger team wants a transaction. The like-counter team wants to stay up during a blip.

Find: Say which writes are ACID and which are BASE with a repair story.

Tiny example: Transfer $20 vs increment a view count, replica unavailable for 8s.

Name of the tool

ACID is a local transactional contract. BASE is an availability-first style for partitioned, eventually consistent stores. They are not religions; they are placement decisions.

Why this tool

Interviews still contrast SQL/ACID with NoSQL/BASE.

Approach

  1. List invariants that cannot be eventual (balance ≥ 0, seat unique, username unique).
  2. Put those on an ACID store or a consensus/CAS primitive.
  3. Put high-volume, mergeable, or reconstructable data on BASE stores and streams.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Is this write a transaction or an eventually reconciled counter?
  • What do you lose if you skip the transaction?
  • BASE like-count drifted by 4% — is that OK?

You say this first

ACID is a local transactional contract. BASE is an availability-first style for partitioned, eventually consistent stores. They are not religions; they are placement decisions. I'd only add it if a requirement we wrote down actually needs it. ACID: billing, inventory, authz grants, unique handles.

Tradeoff: ACID: fewer reconciliation jobs, harder horizontal write scale.. Failure mode: Using the 'C' in ACID as if it were CAP consistency. Never say 'NoSQL means BASE so we cannot have transactions' — many NoSQL stores have single-key atomicity.

Interviews still contrast SQL/ACID with NoSQL/BASE. The hireable answer is: keep ACID where invariants are sharp and the write set is small; use BASE where scale and partition tolerance dominate and you can reconcile.

Skip when: Do not put ledger lines in an eventually consistent document DB 'for scale.'
