The problem they give you

They will not say “Long polling, WebSockets, and SSE.” They describe this:

Given: The UI needs new data without the user hitting refresh. You have HTTP, and you have sockets.

Find: Pick long poll, WebSocket, or SSE for this product, and say who holds the connection.

Tiny example: 200k idle clients, a chat vs a sports score vs an invoice status.

Name of the tool

Three ways to push bytes to a browser or app without the client asking every second — connections, proxies, and fan-out.

Why this tool

Chat, presence, live comments, and notifications need a push channel.

Approach

  1. Terminate connections on a stateful-ish gateway fleet; keep app logic behind.
  2. Subscribe each connection to topics (user, room) on Redis/NATS/Kafka.
  3. Heartbeat; expire dead sockets; handle reconnect with a cursor/seq.

Tradeoff: WS: duplex and efficient, proxy/ops pain.. Failure mode: No heartbeat — half-open TCP forever. Draw: clients → WS gateway → pubsub → workers/DB.

More notes if you want them

Chat, presence, live comments, and notifications need a push channel. Picking WS vs SSE vs poll is an HLD staple. The hard part is holding millions of connections and fanning events from a bus to the right sockets.

Use when: WS: chat, multiplayer, duplex control (Zoom signaling).

Skip when: Do not hold a WS per user just to refresh a daily dashboard — poll or push rarely.

Trap: No heartbeat — half-open TCP forever.
