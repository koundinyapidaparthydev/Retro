The problem they give you

They will not say “Synchronous vs asynchronous APIs.” They describe this:

Given: The client clicked Pay and is staring at a spinner while you email, score fraud, and write search.

Find: Decide which calls stay request/response and which return 202 and finish later.

Tiny example: Pay p99 budget 300ms, fraud model 900ms, email 2s, user will refresh.

Name of the tool

Wait for the answer now (request/response) versus accept work and finish later (jobs, events, 202 Accepted).

Approach

  1. If p99 work > ~200–500ms or calls a flaky partner, make it async.
  2. Return 202 + Location/status; or an optimistic UI with a pending row.
  3. Put the work on a queue/stream with idempotency keys.

More notes if you want them

The biggest latency and reliability lever in HLD is 'does the user wait for this?' Email, transcode, fan-out, and partner calls should almost never sit on the request thread. Interviews listen for 202 + poll/webhook versus a 30s HTTP.

Use when: Sync: reads, login, small CRUD, anything in the latency budget.

Skip when: Do not block HTTP on sending 1M fan-out writes.

Trap: Gateway timeout 60s wrapping a 90s transcode.
