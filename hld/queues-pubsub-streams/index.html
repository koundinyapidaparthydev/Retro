Queues vs pub/sub vs streams

CORE

The problem they give you

They will not say “Queues vs pub/sub vs streams.” They describe this:

Given: After checkout you must email, bill, and update search. Doing it all in the request is 4s and loses the email on timeout.

Find: Pick a work queue, a broadcast, or a replayable log — not “add Kafka.”

Tiny example: 3k checkouts/s, email can be 30s late, search must rewind yesterday after a bug.

Name of the tool

Three ways to decouple producers and consumers: competing consumers, fan-out topics, and replayable logs.

Why this tool

Candidates say 'we'll add Kafka' for every async arrow.

Approach

  1. Jobs with one worker type → queue + DLQ + visibility timeout.
  2. One event, many independent side effects → pub/sub (durable).
  3. Ordered facts you will re-read or share across teams → stream with a partition key.

You say this first

Three ways to decouple producers and consumers: competing consumers, fan-out topics, and replayable logs. I'd only add it if a requirement we wrote down actually needs it. Queue: emails, image jobs, webhook delivery, report exports.

Tradeoff: Queue: simple workers, no replay, weaker fan-out.. Failure mode: One giant topic with no key — random order and hot brokers. Name the consumer cardinality: competing vs broadcast vs independent groups.

More notes if you want them

Candidates say 'we'll add Kafka' for every async arrow. The shape matters: a job queue, a broadcast, or an ordered log you can rewind. Wrong shape gives lost broadcasts, stuck poison messages, or a $10k/day log you treat like Rabbit.

Use when: Queue: emails, image jobs, webhook delivery, report exports.

Skip when: Do not use ephemeral pub/sub for billing events.

Trap: One giant topic with no key — random order and hot brokers.
