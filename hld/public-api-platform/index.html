The problem they give you

They will not say “Design a public API platform.” They describe this:

Given: Third parties will call your API with keys, quotas, and webhooks they expect to trust.

Find: v1: auth, rate limits, versioning, audit. A marketplace of apps is later.

Tiny example: 20k partner QPS, one partner is 40% of traffic, a leaked key at 3am.

Name of the tool

Keys, OAuth, per-consumer quotas, versioning, webhooks, and a developer portal — the gateway as a product, not a single nginx.

Why this tool

Platforms (Stripe-like) are judged on the edge: auth, limits, audit, and compatibility.

Approach

  1. Edge TLS + WAF → gateway validates key/OAuth (iss/aud/exp) → quota → route to service.
  2. Attach consumer_id and request_id; services authorize scopes again.
  3. Async log the request metadata; sample bodies.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Design a public API platform.
  • API key vs OAuth — who is the caller?
  • You ship a breaking change. How do old clients live?

You say this first

I'd treat this as a 45-minute HLD. First I lock v1 of public API platform: who uses it, read vs write, latency, what is v2. Keys, OAuth, per-consumer quotas, versioning, webhooks, and a developer portal — the gateway as a product, not a single nginx.

Then API, data, one write path and one read path. Deep dive: Edge TLS + WAF → gateway validates key/OAuth (iss/aud/exp) → quota → route to service.. URL vs header versioning: clarity vs pretty URLs.

More notes if you want them

Platforms (Stripe-like) are judged on the edge: auth, limits, audit, and compatibility. This design pulls traffic, reliability, and product-ops together.

Use when: Stripe/Twilio-like interviews, marketplace partner APIs, internal API-as-product.

Skip when: Do not build a full platform for a single internal app.

Trap: Plaintext API keys in the DB.
