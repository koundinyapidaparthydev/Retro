The problem they give you

They will not say “PII and GDPR-style privacy.” They describe this:

Given: A user in the EU hits “delete my account.” Copies of their email live in logs, backups, and a warehouse.

Find: Decide what is PII, where it lives, and how delete or export actually completes.

Tiny example: 30-day log retention, 90-day backups, a replica in the US.

Name of the tool

Minimize personal data, know where it copies, honor deletion/export, and treat logs and analytics as in-scope — not only the user table.

Why this tool

Privacy is an HLD constraint like latency.

Approach

  1. Maintain a data map: systems that store user_id or PII fields.
  2. Build export and delete jobs that walk the map; make them idempotent.
  3. Define retention per table (logs 14–30d, backups 30–90d, etc.).

Tradeoff: More copies for product (search, recs): better UX, harder erasure.. Failure mode: User id in URLs and screenshots as if it were secret, but also email in logs. When you add CDC and lakes, add 'delete fan-out' in the same breath.

More notes if you want them

Privacy is an HLD constraint like latency. If you CDC users into a lake and six caches, 'DELETE FROM users' is theater. Interviewers like a data-map and a deletion workflow.

Use when: Any consumer or employee personal data — assume regulation applies.

Skip when: Do not claim 'we are not in Europe' as a design for a global app.
