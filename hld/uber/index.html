Design Uber matching

ADV

The problem they give you

They will not say “Design Uber matching.” They describe this:

Given: A rider opens the app. Nearby drivers are moving. Someone has to be offered the trip.

Find: v1: ping location, request a ride, match one driver. Pricing is later.

Tiny example: Location updates dwarf match QPS. Two riders grab the last driver downtown.

Name of the tool

Riders request, drivers stream location, a matcher pairs them with geo indexes, then a trip lifecycle and pricing — realtime plus inventory of cars.

Why this tool

Uber is maps + matching + trip state.

Approach

  1. Drivers heartbeat location into a cell index; expire if silent.
  2. Request: compute cells around pickup, query available drivers, rank (ETA, score), offer to top, wait accept with timeout, next candidate.
  3. On accept, CAS driver status busy; create trip; both sides subscribe to trip WS.

You say this first

Two loops: drivers ping location, riders request a trip. Matching queries nearby supply and offers one driver at a time.

trips. drivers. Redis GEO or S2 cells for nearby. Trip state machine. Rider API → matching → geo index → offer to driver app. Location ingest separate. Offer with TTL. If ignored, next driver. Lock the trip so two drivers don't win. Surge is a read of density, not a rewrite of matching. If they ask “Two riders grab the last driver.”: Conditional update on driver state. Loser re-queries.

More notes if you want them

Uber is maps + matching + trip state. The deep dive is 'find nearby available drivers' at city scale without scanning the world every request.

Use when: Rideshare, delivery, 'nearby providers' dispatch.

Skip when: Do not SELECT * FROM drivers WHERE distance < 5km on MySQL every request.

Trap: Two riders matching the same driver without CAS.
