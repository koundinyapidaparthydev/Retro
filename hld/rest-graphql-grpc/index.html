The problem they give you

They will not say “REST, GraphQL, gRPC, WebSockets, and SSE.” They describe this:

Given: Mobile wants one round trip with nested data. Internal services want typed, fast RPC. A partner wants a boring HTTP API.

Find: Pick REST, GraphQL, gRPC, WebSocket, or SSE per client — not one religion.

Tiny example: Public third parties, a mobile homepage of 12 resources, 40 internal RPCs/s per page.

Name of the tool

Pick a contract style: resource HTTP, client-shaped queries, binary RPC, or a long-lived stream — each with a different chattiness and caching story.

Why this tool

Protocol choice is an HLD decision, not a framework default.

Approach

  1. Public CRUD and partner APIs: REST with pagination and idempotency keys.
  2. Complex mobile screens: GraphQL or a BFF that aggregates REST.
  3. Internal sync: gRPC with deadlines and retries on idempotent RPCs.

You say this first

Pick a contract style: resource HTTP, client-shaped queries, binary RPC, or a long-lived stream — each with a different chattiness and caching story. I'd only add it if a requirement we wrote down actually needs it. REST for resources you can name and cache.

Tradeoff: REST: cache and ops simplicity, chattiness.. Failure mode: Unbounded GraphQL queries as a public DoS. Pick REST for URL shortener; gRPC internal; WS for chat — show you can mix.

More notes if you want them

Protocol choice is an HLD decision, not a framework default. Mobile chat vs public CRUD vs internal mesh vs live prices all want different shapes. You should know cacheability, streaming, and codegen — and when mixing is correct.

Use when: REST for resources you can name and cache.

Skip when: Do not expose raw gRPC to third-party browsers.

Trap: Unbounded GraphQL queries as a public DoS.
