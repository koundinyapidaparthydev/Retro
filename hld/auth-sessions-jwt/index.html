Auth: sessions, JWT, OAuth2, OIDC, API keys

CORE

The problem they give you

They will not say “Auth: sessions, JWT, OAuth2, OIDC, API keys.” They describe this:

Given: Users log in on web and mobile. A third-party app wants access. Someone pasted a JWT in a URL.

Find: Pick sessions, JWT, OAuth/OIDC, or API keys per client, and how you revoke.

Tiny example: Session in Redis vs 24h JWT, a stolen laptop, logout must work now.

Name of the tool

How you know who is calling — cookies vs tokens, delegated access vs login, and what to store on the server.

Why this tool

Every design has an 'auth box' that candidates skip.

Approach

  1. First-party web: session cookie or BFF that holds the refresh token.
  2. Mobile/SPA: OIDC code+PKCE; short-lived access JWT; rotate refresh.
  3. Service-to-service: mTLS or client-credentials JWT, not a user cookie.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Session cookie or JWT for this app?
  • How does logout work if the JWT is already issued?
  • OAuth for the partner, API key for the cron.

You say this first

How you know who is calling — cookies vs tokens, delegated access vs login, and what to store on the server. I'd only add it if a requirement we wrote down actually needs it. Sessions for classic web apps with immediate logout.

Tradeoff: Server sessions: easy revoke, extra lookup and store.. Failure mode: Storing JWT in localStorage (XSS = account take). Ask first-party vs third-party client — that picks cookie vs OAuth.

More notes if you want them

Every design has an 'auth box' that candidates skip. The choice changes logout, revocation, mobile, partners, and whether a leaked token is a forever skeleton key. Know the flows well enough to draw them.

Use when: Sessions for classic web apps with immediate logout.

Skip when: Do not put a 30-day JWT in localStorage and call it stateless security.

Trap: Storing JWT in localStorage (XSS = account take).
