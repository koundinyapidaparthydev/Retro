The problem they give you

They will not say “Change data capture.” They describe this:

Given: Search, cache, and the warehouse all need “what just changed in orders” without the API remembering to tell them.

Find: Tap the database log, and say what you do about schema changes and deletes.

Tiny example: Primary WAL 80 MB/s, three consumers, a DROP COLUMN on Tuesday.

Name of the tool

Turn the database log into a stream of row changes so search, caches, warehouses, and other services stay in sync without dual-write.

Why this tool

CDC is how modern platforms feed Elasticsearch, caches, and analytics without the app remembering every projection.

Approach

  1. Enable WAL-level logical decoding / binlog; create a publication of needed tables.
  2. Snapshot then stream; sink upserts by PK; apply deletes.
  3. Evolve schema with compatible changes or a contract registry.

You say this first

Turn the database log into a stream of row changes so search, caches, warehouses, and other services stay in sync without dual-write. I'd only add it if a requirement we wrote down actually needs it. Search indexes, cache fill, OLAP, cross-service data copies.

Tradeoff: Log-based: accurate and light on the source, ops-heavy (slots, connectors).. Failure mode: Replication slot disk exhaustion taking down the primary. For Instagram search or Netflix catalog, say 'CDC from OLTP to Elasticsearch/warehouse.'

More notes if you want them

CDC is how modern platforms feed Elasticsearch, caches, and analytics without the app remembering every projection. It is also how you implement a scalable outbox. You should know log-based vs query-based and the ordering/schema problems.

Use when: Search indexes, cache fill, OLAP, cross-service data copies.

Skip when: Do not CDC the entire database to every microservice as a hidden shared DB.

Trap: Replication slot disk exhaustion taking down the primary.
