The problem they give you

They will not say “Design autocomplete / typeahead.” They describe this:

Given: The search box must suggest as they type, not after they hit enter.

Find: v1: prefix matches in tens of milliseconds. Personalized ranking is later.

Tiny example: Typeahead at 8k QPS, prefixes of 1–3 letters are huge, p99 under 50ms.

Name of the tool

Prefix search at keystroke QPS: tries or n-gram indexes, heavy cache, and ranking that can personalize without melting the prefix shard.

Why this tool

QPS is enormous (every keypress) and latency budgets are tiny (~50–100ms).

Approach

  1. Client debounces; API checks CDN/Redis; else memory trie; else search index.
  2. Return top K with display strings and types.
  3. Nightly/hourly job rebuilds popularity; stream bumps trending.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Design Google typeahead.
  • Trie in memory vs inverted index — what is v1?
  • A misspelled prefix and a hot prefix that stampedes.

You say this first

I'd treat this as a 45-minute HLD. First I lock v1 of autocomplete / typeahead: who uses it, read vs write, latency, what is v2. Prefix search at keystroke QPS: tries or n-gram indexes, heavy cache, and ranking that can personalize without melting the prefix shard.

Then API, data, one write path and one read path. Deep dive: Client debounces; API checks CDN/Redis; else memory trie; else search index.. Memory trie: ultra fast, laggy updates and size limits.

More notes if you want them

QPS is enormous (every keypress) and latency budgets are tiny (~50–100ms). This is a cache + prefix index problem, not a general search problem — though they share an inverted index cousin.

Use when: Search boxes, @mentions, maps place typeahead, command palettes at scale.

Skip when: Do not run full ES retrieval + ML rank on every keypress without a cheap first stage.

Trap: Caching personalized suggestions at CDN under the raw prefix key.
