The problem they give you

They will not say “Design YouTube-like streaming.” They describe this:

Given: Creators upload long video; viewers hit play and expect it to start fast on a bad network.

Find: v1: upload, transcode, store renditions, play via CDN. Comments are later.

Tiny example: Hours of 4K a day, ABR on 3G, a premiere spikes one origin.

Name of the tool

Upload, transcode into an ABR ladder, package HLS/DASH, serve via CDN, plus watch history and a little metadata — not the ML recommender in v1.

Why this tool

Video is a pipeline + CDN + player protocol problem.

Approach

  1. Multipart upload master → jobs: probe, virus, transcode ladder, thumbs, package.
  2. When a playable rendition exists, status=ready; player fetches manifest from CDN.
  3. Heartbeats go to a stream for history and metrics; sample if needed.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Design YouTube.
  • Where do original bytes vs renditions live?
  • Play starts in Mumbai while the origin is in Iowa.

You say this first

I'd treat this as a 45-minute HLD. First I lock v1 of YouTube-like streaming: who uses it, read vs write, latency, what is v2. Upload, transcode into an ABR ladder, package HLS/DASH, serve via CDN, plus watch history and a little metadata — not the ML recommender in v1.

Then API, data, one write path and one read path. Deep dive: Multipart upload master → jobs: probe, virus, transcode ladder, thumbs, package.. More renditions: better ABR, more cost.

More notes if you want them

Video is a pipeline + CDN + player protocol problem. Interviews go wrong when people talk only about Kafka and never about segments, bitrates, and origin.

Use when: VOD products, courses, UGC video, interview 'design YouTube.'

Skip when: Do not stream the master file as the only rendition.

Trap: No duration/size cap.
