The problem they give you

They will not say “Search and inverted indexes.” They describe this:

Given: SQL LIKE '%shoe%' is 900ms and still ranks badly. Users type three words and expect relevance.

Find: Design search as its own index, and say how it lags the source of truth.

Tiny example: 50M documents, 8k queries/s, a new listing must appear within ~10s.

Name of the tool

Map terms to posting lists so you can find documents by words, filters, and rank — a different engine than OLTP.

Why this tool

SQL LIKE will not do product search.

Approach

  1. OLTP owns documents; a pipeline upserts ES docs by id.
  2. Design mappings: analyzers for text, keyword for filters, geo for maps.
  3. Shard by a key that balances size; avoid one giant time shard if you can roll indexes.

You say this first

Map terms to posting lists so you can find documents by words, filters, and rank — a different engine than OLTP. I'd only add it if a requirement we wrote down actually needs it. Full-text, faceted product search, log analytics, autocomplete.

Tradeoff: Relevance and flexibility vs lag, ops, and scatter-gather tails.. Failure mode: Deep from/size pagination on huge result sets. For autocomplete/Instagram/maps, draw DB → CDC → index → search API.

More notes if you want them

SQL LIKE will not do product search. Autocomplete, Instagram captions, and log search need an inverted index, ranking, and a freshness pipeline. Interviews want ES/Solr/OpenSearch or a managed equivalent plus CDC, not a sequential scan.

Use when: Full-text, faceted product search, log analytics, autocomplete.

Skip when: Primary store for records that need transactions.

Trap: Deep from/size pagination on huge result sets.
