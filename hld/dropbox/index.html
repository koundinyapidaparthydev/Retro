Design Dropbox

ADV

The problem they give you

They will not say “Design Dropbox.” They describe this:

Given: A file saved on the laptop should show up on the phone, including edits to the middle of a 2 GB video.

Find: v1: chunk, sync, conflict on two writers. Full office suite is later.

Tiny example: Millions of tiny metadata ops, large objects in blob store, two devices edit offline.

Name of the tool

A syncing filesystem illusion: chunked content-addressed blobs, a metadata store for the tree, and clients that sync deltas.

Why this tool

Dropbox is metadata + object store + sync protocol.

Approach

  1. Client chunks file, hashes, uploads missing blocks, commits a revision (CAS parent rev).
  2. Other devices watch the namespace journal and pull new revs/blocks.
  3. Share: ACL edge; signed links for external.

You say this first

I'd treat this as a 45-minute HLD. First I lock v1 of Dropbox: who uses it, read vs write, latency, what is v2. A syncing filesystem illusion: chunked content-addressed blobs, a metadata store for the tree, and clients that sync deltas.

Then API, data, one write path and one read path. Deep dive: Client chunks file, hashes, uploads missing blocks, commits a revision (CAS parent rev).. Content-addressed dedup: savings vs encryption-per-user (dedup dies if you encrypt client-side with different keys).

More notes if you want them

Dropbox is metadata + object store + sync protocol. The interesting bugs are conflicts, rename, and 'do not re-upload the same bytes.' It is not 'S3 with a UI.'

Use when: File sync, backup clients, Drive-like products.

Skip when: Do not store each file as one object without chunking if you need delta sync.

Trap: Tree in object listings.
