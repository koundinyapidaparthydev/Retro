The problem they give you

They will not say “Transactional outbox.” They describe this:

Given: The API committed the order and then failed to publish “order_created.” Warehouse never shipped.

Find: Make the DB write and the “tell others” message the same transaction story.

Tiny example: 5k orders/s, Kafka blip of 90s, a dual-write that looks fine in happy path.

Name of the tool

Write the business row and the 'please publish' row in one database transaction, then a relay publishes to the broker. Dual-write without the lie.

Why this tool

The classic bug is COMMIT user then fail to publish 'UserCreated' — or publish then rollback.

Approach

  1. Begin txn → mutate domain tables → insert outbox row → commit.
  2. Relay publishes with the outbox id as the broker key/id.
  3. Mark published (or delete) after ack; retry on failure.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • DB committed, Kafka publish failed. Now what?
  • Transactional outbox vs dual write.

You say this first

Write the business row and the 'please publish' row in one database transaction, then a relay publishes to the broker. Dual-write without the lie. I'd only add it if a requirement we wrote down actually needs it. Any domain event that must not diverge from the OLTP write.

Tradeoff: Polling: simple, extra DB load and delay.. Failure mode: Publishing from the app after commit 'and hoping.' When you draw 'API writes DB and Kafka,' immediately say outbox.

More notes if you want them

The classic bug is COMMIT user then fail to publish 'UserCreated' — or publish then rollback. Outbox is the interview-grade fix before you reach for distributed transactions. It pairs with CDC as an implementation.

Use when: Any domain event that must not diverge from the OLTP write.

Skip when: Do not outbox high-frequency metrics — use a metrics pipeline.

Trap: Publishing from the app after commit 'and hoping.'
