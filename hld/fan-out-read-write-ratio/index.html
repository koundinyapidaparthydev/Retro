Fan-out and read/write ratio

CORE

The problem they give you

They will not say “Fan-out and read/write ratio.” They describe this:

Given: One tweet and one page view are not one write and one read. Hidden multipliers will melt you.

Find: Write the read/write ratio and the fan-out on the board before you pick caches or queues.

Tiny example: Post × 1M followers, a page that calls 12 services, cache miss stampede × 1k.

Name of the tool

How many downstream writes or reads one user action creates — and whether the product is read-heavy, write-heavy, or celebrity-heavy.

Why this tool

Read/write ratio decides caches, replicas, and CQRS.

Approach

  1. Split traffic into read APIs vs write APIs; estimate each.
  2. For each write, list fan-out targets: followers, devices, search index, cache invalidations, analytics.
  3. For each read, list fan-in: how many keys, shards, or services you touch.

You say this first

How many downstream writes or reads one user action creates — and whether the product is read-heavy, write-heavy, or celebrity-heavy. I'd only add it if a requirement we wrote down actually needs it. Feeds, chat receipts, notifications, ACLs that expand to many objects.

Tradeoff: Fan-out-on-write: fast reads, huge write amplification and storage, celebrity pain.. Failure mode: Designing Instagram as if every user has 200 followers. Ask 'how many followers at p99?' before you commit to push vs pull.

More notes if you want them

Read/write ratio decides caches, replicas, and CQRS. Fan-out decides whether you push work at write time (newsfeed) or pull at read time (on-demand join). Celebrities break naive fan-out-on-write. If you skip this, your boxes are fiction.

Use when: Feeds, chat receipts, notifications, ACLs that expand to many objects.

Skip when: Do not fan-out-on-write to millions of inboxes synchronously on the request path.

Trap: Designing Instagram as if every user has 200 followers.
