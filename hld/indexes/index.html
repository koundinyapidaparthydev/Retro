The problem they give you

They will not say “Indexes.” They describe this:

Given: The query that was fine at 1M rows now scans 400M. Writes are slower every time you “just add an index.”

Find: Pick which indexes exist from the real WHERE/ORDER BY, and what you refuse to index.

Tiny example: orders(user_id, created_at, status), 20k writes/s, a dashboard filters 12 columns.

Name of the tool

Secondary structures that turn scans into seeks — B-trees, hashes, inverted and composite keys — and the write tax they add.

Why this tool

A design that says 'query by user and time' without an index is a table scan at 10^9 rows.

Approach

  1. Write the top 5 queries; give each a supporting index or a specialized store.
  2. Prefer composite indexes that match filter + sort.
  3. Measure write amplification; drop unused indexes.

You say this first

Secondary structures that turn scans into seeks — B-trees, hashes, inverted and composite keys — and the write tax they add. I'd only add it if a requirement we wrote down actually needs it. OLTP lookups and range lists that are not by primary key.

Tradeoff: More indexes: faster reads, slower writes and bigger storage.. Failure mode: LIKE '%foo%' on a B-tree. When you write a table, write the PK and one secondary index next to it.

More notes if you want them

A design that says 'query by user and time' without an index is a table scan at 10^9 rows. Indexes are also why writes slow down and why disks grow 2×. You should name the index that makes the hot query cheap.

Use when: OLTP lookups and range lists that are not by primary key.

Skip when: Do not index every column 'just in case.'
