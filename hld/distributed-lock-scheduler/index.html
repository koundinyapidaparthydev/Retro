Design a distributed lock and job scheduler

ADV

Definition

Leases not locks-forever: fencing tokens, and a scheduler that runs cron-like jobs once across a fleet.

Why it exists

Every platform grows 'run this once a minute' and 'only one leader mutates X.' The interview is correctness under pause and partition — Redis SET NX i…

Approach

  1. Lock: CAS create with TTL + increment fencing token; client sends token on every write.
  2. Renew heartbeat; if expired, another may acquire a higher token.
  3. Scheduler: worker claims due jobs (SKIP LOCKED or shard leader), runs, acks, sets next_run.

More notes if you want them

Every platform grows 'run this once a minute' and 'only one leader mutates X.' The interview is correctness under pause and partition — Redis SET NX is not enough if you do not fence.

Use when: Leader election, unique periodic work, 'design a cron for 10k jobs.'

Skip when: Do not hold a Redis lock across a user HTTP request that might last minutes.

Trap: Lock without TTL — deadlock when a process dies.
