The problem they give you

They will not say “Design maps nearby search.” They describe this:

Given: The user wants coffee within 1 km, ranked by walking time, not a table scan of Earth.

Find: v1: index points, query a radius, return a page. Turn-by-turn is later.

Tiny example: 50k nearby queries/s, downtown is dense, desert cells are empty.

Name of the tool

Find places near a lat/lng: geo indexes (geohash, S2, R-tree), ranking, and a cache of popular tiles — plus the moving-user problem.

Why this tool

Geo is a specialized access pattern.

Approach

  1. Index each POI into covering cells plus type/text fields.
  2. On query, list cells that cover the circle; fetch ids; exact-distance filter; rank; return K.
  3. Cache popular (cell, type, r) results with a short TTL.

You say this first

I'd treat this as a 45-minute HLD. First I lock v1 of maps nearby search: who uses it, read vs write, latency, what is v2. Find places near a lat/lng: geo indexes (geohash, S2, R-tree), ranking, and a cache of popular tiles — plus the moving-user problem.

Then API, data, one write path and one read path. Deep dive: Index each POI into covering cells plus type/text fields.. Coarser cells: fewer lookups, more false candidates.

More notes if you want them

Geo is a specialized access pattern. Interviews want you to not scan the world table and to know cells, false neighbors, and how Uber/maps reuse the same index ideas.

Use when: Maps, delivery, dating nearby, store locators, Uber driver search.

Skip when: Do not scan a global SQL table with a distance formula as the only plan.

Trap: Forgetting geohash edge neighbors (points just outside the cell).
