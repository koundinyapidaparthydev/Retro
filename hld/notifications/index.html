Design a notification system

CORE
MetahotAmazonoftenGoogleoftenPush + fan-out + quiet hours.

The problem they give you

They will not say “Design a notification system.” They describe this:

Given: An event happens — like, comment, ship — and the user should hear about it on phone, email, or in-app.

Find: v1: ingest events, fan-out to devices, respect quiet hours. No ML ranking.

Tiny example: 2M push/min at a concert drop. One user has 4 devices and muted the sender.

Name of the tool

Fan-out events to in-app inbox, push, email, and SMS with preferences, batching, and at-least-once delivery you can mute.

Why this tool

Every product grows a notification platform.

Approach

  1. Product outbox → bus → notification service expands recipients (or receives them).
  2. Filter prefs/quiet/dedup → write inbox → enqueue channel jobs.
  3. Channel workers send; retry; DLQ; update delivery status.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Design a notification system.
  • Push vs email vs in-app — who decides the channel?
  • The provider 429s. Do we drop, retry, or DLQ?

You say this first

I'd treat this as a 45-minute HLD. First I lock v1 of notification system: who uses it, read vs write, latency, what is v2. Fan-out events to in-app inbox, push, email, and SMS with preferences, batching, and at-least-once delivery you can mute.

Then API, data, one write path and one read path. Deep dive: Product outbox → bus → notification service expands recipients (or receives them).. Per-event push vs digest: latency vs peace and cost.

More notes if you want them

Every product grows a notification platform. The design is an event bus, preference store, per-channel workers, and a user inbox — plus the 'do not wake them at 3am' rules.

Use when: Any consumer app; also a standalone platform interview.

Skip when: Do not send email in the request that created the like.

Trap: No unsubscribe/quiet hours.
