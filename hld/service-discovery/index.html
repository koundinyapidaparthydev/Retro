The problem they give you

They will not say “Service discovery.” They describe this:

Given: IPs change every deploy. Hard-coded hosts in config are already wrong.

Find: Decide how callers find healthy instances after a scale event.

Tiny example: Kubernetes pods churn, a DNS TTL of 60s, a client cache that never expires.

Name of the tool

How clients find healthy instances as IPs change — DNS, registries, and mesh endpoints — without hardcoding boxes.

Why this tool

Horizontal scale implies churn.

Approach

  1. Give every service a stable DNS name; never ship instance IPs in app config.
  2. Register on start, deregister on SIGTERM after drain.
  3. Prefer platform primitives (K8s Service, cloud LB) unless you need custom client policies.

More notes if you want them

Horizontal scale implies churn. If you skip discovery you get stale IPs, split traffic during deploys, and heroic config files. In the cloud the LB often is discovery; in a mesh or on-prem you must say the registry name.

Use when: Any microservice or worker fleet with rolling deploys.

Skip when: A single-node app — a config host is enough.

Trap: Stale client caches after a scale-in.
