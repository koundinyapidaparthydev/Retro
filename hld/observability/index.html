Observability: logs, metrics, and traces

CORE

The problem they give you

They will not say “Observability: logs, metrics, and traces.” They describe this:

Given: Users say it is slow. You have 12 dashboards and no trace that ties a request across four services.

Find: Put logs, metrics, and traces on the user action, not on “CPU looks fine.”

Tiny example: RED on the checkout route, a trace id from mobile to ledger, a missing span on the queue hop.

Name of the tool

Logs tell stories, metrics tell numbers over time, traces tell a request's path. Together they answer 'why is it broken?' without SSH.

Why this tool

You cannot operate or defend an HLD without saying how you will see it fail.

Approach

  1. Propagate a correlation/trace id from the edge (API gateway) to DB and queues.
  2. Export RED metrics per endpoint and USE metrics per dependency (pool wait, replica lag, queue depth).
  3. Alert on SLOs and saturation, not on raw CPU, unless CPU is the proven limiter.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • How do you find why this one request was 3s?
  • What is the SLI metric vs a debug log?
  • A worker ate the message and there is no trace after the queue.

You say this first

Logs tell stories, metrics tell numbers over time, traces tell a request's path. Together they answer 'why is it broken?' without SSH. I'd only add it if a requirement we wrote down actually needs it. Metrics + SLO alerts for every production user path.

Tradeoff: Full traces: perfect debug, huge cost; sampling: cheap, may miss the rare monster.. Failure mode: Alerting on CPU while the SLO is still green — pager fatigue. For any design, list 5 signals: QPS, error rate, p99, queue lag, replica lag / cache hit rate.
