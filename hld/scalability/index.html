Scalability: vertical vs horizontal

CORE

Definition

How a system absorbs more load — bigger machines versus more machines — and what each choice forces on data, state, and operations.

Why it exists

Almost every HLD interview starts with 'this will grow.' Vertical scale buys time; horizontal scale is the design.

Approach

  1. Find the bottleneck with numbers: QPS, payload size, working set, connection count, and p99 — not 'it feels slow.'
  2. Scale compute first if the app is stateless: more replicas, autoscaling on CPU or queue depth, sticky sessions only if you must.
  3. Scale reads with replicas and caches; scale writes with sharding, queues, and batching.

Vertical first for early products, single-primary databases, and when operational simplicity beats peak efficiency.

Tradeoff: Vertical: simple consistency and ops; hard ceiling and bigger blast radius.. Failure mode: Scaling pods while the database or a single Redis key is the real limiter. Say what you scale and why: 'writes hit one primary, so we shard by user_id; reads go to replicas and Redis.'

More notes if you want them

Almost every HLD interview starts with 'this will grow.' Vertical scale buys time; horizontal scale is the design. You need to say which bottleneck you are scaling (CPU, RAM, disk, network, connections) and what becomes hard once you add machines.

Use when: Vertical first for early products, single-primary databases, and when operational simplicity beats peak efficiency.

Skip when: Do not shard a database because the interview said 'scale' — shard when a single primary cannot take the writes or the working set.

Trap: Scaling pods while the database or a single Redis key is the real limiter.
