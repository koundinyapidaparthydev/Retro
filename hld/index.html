Method1

The 7-step HLD interview method

CORE

A repeatable structure for 45-minute system design: clarify, estimate, API, data, design, deepen, wrap — so you lead the room instead of drowning in boxes.

Quality attributes6

Availability vs reliability

CORE

Availability is 'can I reach a healthy enough answer now?' Reliability is 'does the system keep its promises over time?' Interviews mix them; good answers split them.

Consistency vs durability

CORE

Consistency is whether replicas agree on a view of the data. Durability is whether a committed write survives crashes. They are not the same knob.

Latency vs throughput

CORE

Latency is how long one request waits. Throughput is how many the system finishes per second. Optimizing one can hurt the other — batching is the usual example.

Observability: logs, metrics, and traces

CORE

Logs tell stories, metrics tell numbers over time, traces tell a request's path. Together they answer 'why is it broken?' without SSH.

Scalability: vertical vs horizontal

CORE

How a system absorbs more load — bigger machines versus more machines — and what each choice forces on data, state, and operations.

Fault tolerance, DR, RPO and RTO

NEXT

Fault tolerance keeps serving through component failure. Disaster recovery is the plan when a whole site or region is gone. RPO and RTO turn that plan into numbers.

Distributed models11

CAP theorem

CORE

If the network splits, you must choose: keep serving maybe-stale data (Availability) or refuse until you are sure (Consistency). You cannot fully have both during a partition.

ACID vs BASE

CORE

ACID is a local transactional contract. BASE is an availability-first style for partitioned, eventually consistent stores. They are not religions; they are placement decisions.

Backpressure, retries, timeouts, and circuit breakers

CORE

How a system says 'slow down' instead of melting, and how retries without jitter and budgets become a self-DDoS.

Consistency models

CORE

Strong, eventual, causal, read-your-writes, and monotonic reads — what users are allowed to observe as replicas and caches catch up.

Failure modes: crash, partition, split-brain, clock skew

CORE

The failures your protocol must survive — not 'the server goes down,' but the messy ones that duplicate leaders and reorder time.

Idempotency and delivery semantics

CORE

At-most-once, at-least-once, and exactly-once-enough: how retries and consumer offsets interact with keys so effects happen once.

Isolation levels

NEXT

Read uncommitted through serializable — which write/read anomalies you accept inside a database, and why distributed SQL still makes you choose.

Leader vs leaderless replication

NEXT

A single primary sequences writes, or every replica can take writes. The choice is latency, conflict handling, and how you fail over.

PACELC

NEXT

If there is a Partition, trade Availability vs Consistency; Else, trade Latency vs Consistency. CAP's missing half is the healthy-path tradeoff.

Quorum reads and writes (N, W, R)

NEXT

With N replicas, a write waits for W acks and a read waits for R responses. If R+W > N you overlap and can read the latest write — with caveats.

Consensus: Raft and Paxos

ADV

How a cluster agrees on one next value (leader, log entry, config) despite crashes and delayed messages — the engine under etcd, ZooKeeper, and many databases.

Estimates4

Back-of-envelope: QPS, storage, bandwidth

CORE

Rough math that turns '100 million users' into QPS, disk, and NIC numbers so the rest of the design has constraints.

Fan-out and read/write ratio

CORE

How many downstream writes or reads one user action creates — and whether the product is read-heavy, write-heavy, or celebrity-heavy.

Percentiles: p50, p95, p99

CORE

Why averages lie, how tail latency becomes the user experience, and how percentiles should drive SLOs and capacity.

Hot keys, hot partitions, and thundering herds

NEXT

When one key, shard, or cache entry absorbs traffic that your average-case math assumed was uniform — plus herds that stampede a backend.

Traffic8

Rate limiting: token bucket, leaky bucket, sliding window

CORE

Algorithms that cap how often a client can act — protecting backends, enforcing fairness, and shaping 429s users can understand.

Load balancers: L4 vs L7

CORE

A receptionist who hands each visitor to a free clerk so no one clerk is crushed.

API gateway and reverse proxy

CORE

The HTTP front door: routing, authn, rate limits, TLS, and request shaping so every microservice does not reinvent the edge.

Auth: sessions, JWT, OAuth2, OIDC, API keys

CORE

How you know who is calling — cookies vs tokens, delegated access vs login, and what to store on the server.

Content delivery networks

CORE

Edge caches that serve static and cacheable HTTP close to users, shield origin, and often terminate TLS.

DNS, anycast, and geo-DNS

CORE

How a name becomes an IP — and how you steer users to a nearby healthy edge before they ever hit your load balancer.

Authorization: RBAC and ABAC

NEXT

Role-based vs attribute-based access control — how you decide what an authenticated principal is allowed to do.

TLS and mTLS

NEXT

Encrypt in transit, authenticate the server (and optionally the client) with certificates — including where you terminate and how identity moves east-west.

Architecture7

Monolith vs modular vs microservices vs SOA

CORE

Where you draw process boundaries — one deployable, modular monolith, service-oriented, or independently deployed microservices — and what that costs in ops and data.

REST, GraphQL, gRPC, WebSockets, and SSE

CORE

Pick a contract style: resource HTTP, client-shaped queries, binary RPC, or a long-lived stream — each with a different chattiness and caching story.

Stateless services and sticky sessions

CORE

Keep request-handling boxes disposable. If you need affinity, know why — and what you will do when that box dies.

Synchronous vs asynchronous APIs

CORE

Wait for the answer now (request/response) versus accept work and finish later (jobs, events, 202 Accepted).

Multi-tenant: silo vs pooled

NEXT

Silo gives each tenant their own stack. Pooled shares infrastructure with tenant keys everywhere. Most SaaS is pooled with silo for whales or compliance.

Service discovery

NEXT

How clients find healthy instances as IPs change — DNS, registries, and mesh endpoints — without hardcoding boxes.

Service mesh (concept)

ADV

Sidecars or a shared proxy layer that give you mTLS, retries, discovery, and telemetry without rewriting every app.

Data stores14

Cache patterns: aside, through, behind, invalidation, TTL, stampede

CORE

Where the cache sits on the read/write path, how it goes stale, and how you stop a TTL expiry from becoming a database outage.

Sharding: range, hash, and directory

CORE

Split a dataset across nodes by a key — range for scans, hash for evenness, directory for flexibility — and live with cross-shard pain.

Replication

CORE

Copy data to more nodes for reads, locality, and durability — sync vs async, leader vs multi-leader, and what lag does to reads.

Indexes

CORE

Secondary structures that turn scans into seeks — B-trees, hashes, inverted and composite keys — and the write tax they add.

Normalize vs denormalize

CORE

Normalize to protect invariants and update-in-one-place. Denormalize to make a read cheap. The art is which copy is allowed to be stale.

Object storage

CORE

S3-style blobs addressed by key: durable, cheap, high latency, weak at mutation and listing-as-a-database.

OLTP vs OLAP, warehouses, and data lakes

CORE

Operational transactions versus analytic scans — and the modern lake/warehouse/lakehouse stack that copies data out of the primary.

Redis vs Memcached

CORE

Memcached is a simple distributed memory map. Redis is a data-structure server (and more). Pick based on structures, persistence, and ops — not vibes.

SQL vs NoSQL

CORE

Pick the store from access patterns and invariants, not from fashion. SQL is relational + a query planner; NoSQL is a family of specialized shapes.

Consistent hashing and virtual nodes

NEXT

Put servers and keys on a ring. A key belongs to the next server clockwise. Add a server and only nearby keys move — not everything.

CQRS

NEXT

Command Query Responsibility Segregation: different models (and often stores) for writes vs reads so each can scale and shape independently.

Search and inverted indexes

NEXT

Map terms to posting lists so you can find documents by words, filters, and rank — a different engine than OLTP.

Time-series, graph, and columnar stores

NEXT

Engines built for append-only metrics, multi-hop relationships, and analytic scans — when a row store is the wrong shape.

Event sourcing

ADV

The write-side source of truth is an append-only log of facts; current state is a fold over those events. Powerful, easy to overuse.

Async8

Queues vs pub/sub vs streams

CORE

Three ways to decouple producers and consumers: competing consumers, fan-out topics, and replayable logs.

Dead-letter queues

CORE

Where poison messages go after retries fail — so one bad payload does not block the partition or the queue forever.

Webhooks vs polling

CORE

Push callbacks when something happens versus the client asking 'any news?' — including signatures, retries, and when to offer both.

Kafka, SQS, and RabbitMQ mental models

NEXT

A log of partitions, a managed competing-consumer queue, and a flexible broker — when each is the boring correct choice.

Batch vs stream processing

NEXT

Nightly jobs over complete datasets versus continuous processing of events — and the hybrid (micro-batch, Kappa, lakehouse).

Change data capture

NEXT

Turn the database log into a stream of row changes so search, caches, warehouses, and other services stay in sync without dual-write.

Sagas: choreography vs orchestration

NEXT

Long-running workflows across services without 2PC — a sequence of local transactions plus compensations when a step fails.

Transactional outbox

NEXT

Write the business row and the 'please publish' row in one database transaction, then a relay publishes to the broker. Dual-write without the lie.

Reliability8

Blue-green, canary, and rolling deploys

CORE

How you ship new bits without a big-bang outage — two environments, a small slice of traffic, or instance-by-instance replacement.

Bulkheads, circuit breakers, retries, and jitter

CORE

Isolate failure domains (pools, queues, threads) and fail fast when a dependency is sick — with retries that do not synchronize.

Fallbacks, graceful degradation, and feature flags

CORE

Serve a worse but useful answer when a dependency fails — stale cache, hide a widget, or flip a flag — instead of a white page.

Health checks and graceful shutdown

CORE

Liveness vs readiness, drain, and SIGTERM — how you leave the load balancer without cutting in-flight work.

Multi-AZ vs multi-region

CORE

Availability zones are independent failure domains in one region. Regions are farther, legally distinct, and much harder for data. Do not confuse them.

Active-active vs active-passive

NEXT

Whether both sites take writes, or only one does while the other stands by — the operational heart of multi-region.

Chaos thinking

ADV

Deliberately inject failure (and latency) to verify that the design you drew actually survives — in staging first, then with a blast radius in prod.

Hedged requests

ADV

Send a backup request after a delay (or in parallel) to beat tail latency — and pay extra QPS for it.

Files4

Block vs file vs object storage

CORE

Three ways to persist bytes: disks you mount, filesystems you share, and HTTP objects you address by key. They are not interchangeable.

CDN and origin design

NEXT

How the edge talks to object storage or an origin fleet: cache keys, shields, signed URLs, and range requests for media.

Chunked and resumable uploads

NEXT

Split large files into parts, upload in parallel, retry a part not the whole file, then assemble — the only sane path for GB uploads on phones.

Image and video processing pipelines

NEXT

Async workers that transcode, thumbnail, and package media into CDN-ready variants — never on the upload request thread.

Realtime4

Unique IDs: UUID, Snowflake, and ticket servers

CORE

How you mint unique, sometimes sortable IDs without a single global auto-increment bottleneck.

Fan-out on write vs fan-out on read

CORE

Push work to many inboxes when an event happens, or pull and merge when someone looks — the core social/realtime fork.

Long polling, WebSockets, and SSE

CORE

Three ways to push bytes to a browser or app without the client asking every second — connections, proxies, and fan-out.

Presence

NEXT

Who is online, idle, or typing — ephemeral state with heartbeats, TTLs, and fan-out that must not become a write storm.

Security5

Encryption at rest and in transit

CORE

TLS on the wire, KMS-backed encryption on disks and objects, and application-level encryption when the platform admin should not see the bytes.

Least privilege and secrets management

CORE

Every identity gets the minimum access it needs, and secrets live in a manager — not in git, images, or Slack.

Audit logs

NEXT

Append-only records of who did what to whom — for security, support, and compliance — separate from debug logs.

DDoS protection and WAF

NEXT

Absorb or drop volumetric floods at the edge, and filter application abuse (injection, bots, scrapers) before it hits origin CPU.

PII and GDPR-style privacy

NEXT

Minimize personal data, know where it copies, honor deletion/export, and treat logs and analytics as in-scope — not only the user table.

Operations5

Alerting vs dashboards

CORE

Alerts page a human for something they must do. Dashboards are for exploration and status. Mixing them is how you train people to ignore the pager.

SLI, SLO, and SLA

CORE

SLIs are measurements, SLOs are internal targets, SLAs are contractual promises — plus error budgets that tell you when to slow down shipping.

Capacity planning

NEXT

Turn estimates and live utilization into a plan for when you add shards, boxes, and budget — before the p99 cliff.

Cost as a design constraint

NEXT

Egress, idle replicas, chatty APIs, and unpartitioned warehouses can dwarf EC2. Good HLD names the expensive lines and a cheaper alternative.

Retention and deletion

NEXT

How long each class of data lives, how it is deleted everywhere, and how you avoid infinite disks and immortal PII.

Classic designs28

Design a URL shortener

CORE

Turn a long link into a short code, save the pair, and when someone opens the short link, send them to the long one — fast, with a cache.

Design a newsfeed (Twitter-like)

CORE

Post once, read a ranked timeline — hybrid fan-out, caches, and a celebrity exception. The classic social HLD.

Design chat / WhatsApp

CORE

1:1 and group messaging: online fan-out over sockets, offline inbox, delivery receipts, and multi-device — with order per conversation.

Design a notification system

CORE

Fan-out events to in-app inbox, push, email, and SMS with preferences, batching, and at-least-once delivery you can mute.

Design a rate limiter

CORE

A distributed service that decides allow/deny (and remaining quota) at tens or hundreds of thousands of QPS without becoming the outage.

Design a unique ID generator

CORE

A service or library that hands out unique, optionally time-sortable 64-bit ids at high QPS without a single SQL sequence.

Design Instagram

CORE

Photo/video social: upload pipeline, follow feed, permalinks, and a CDN — newsfeed plus media, not a new planet.

Design inventory and checkout

CORE

Reserve stock, take payment, fulfill — a saga with a short transactional decrement and a lot of eventual side effects.

Design Pastebin / file share

CORE

Upload text or a file, get a link, download or view — object storage for bytes, metadata in a DB, optional expiry and privacy.

Design a metrics pipeline

NEXT

Agents emit time series, a path aggregates and stores them, and dashboards/alerts read — cardinality is the boss fight.

Design a presence service

NEXT

A standalone online/idle/typing service: heartbeats, TTLs, watchers, and APIs other products can subscribe to.

Design a public API platform

NEXT

Keys, OAuth, per-consumer quotas, versioning, webhooks, and a developer portal — the gateway as a product, not a single nginx.

Design a web crawler

NEXT

Polite, scalable fetch of the public web (or a domain set): frontier queue, politeness per host, parsers, and storage of HTML and links.

Design autocomplete / typeahead

NEXT

Prefix search at keystroke QPS: tries or n-gram indexes, heavy cache, and ranking that can personalize without melting the prefix shard.

Design live comments

NEXT

A high-churn comment stream on a live video or launch: recent window + subscribe, not a full Instagram comment system on every tick.

Design maps nearby search

NEXT

Find places near a lat/lng: geo indexes (geohash, S2, R-tree), ranking, and a cache of popular tiles — plus the moving-user problem.

Design Netflix

NEXT

Catalog + subscription + VOD playback at global scale: encoding, CDN/Open Connect-style, and personalization as a separate plane.

Design trending topics

NEXT

Detect what is spiking now: stream counts in windows, score against a baseline, fight manipulation, and serve a tiny hot list.

Design YouTube-like streaming

NEXT

Upload, transcode into an ABR ladder, package HLS/DASH, serve via CDN, plus watch history and a little metadata — not the ML recommender in v1.

Design a distributed cache

ADV

A Memcached/Redis-cluster-like service: partition keys, replicate if you must, evict, and survive node loss without stampeding origin.

Design a distributed lock and job scheduler

ADV

Leases not locks-forever: fencing tokens, and a scheduler that runs cron-like jobs once across a fleet.

Design a key-value store

ADV

A Dynamo-style distributed KV: partition, replicate, put/get, and handle failures without a single primary for all keys.

Design a payments wallet / ledger

ADV

A system of record for money: double-entry ledger, idempotent credits/debits, and sagas with processors — correctness first.

Design an ad click aggregator

ADV

Ingest a firehose of impressions and clicks, count them correctly enough to bill, and fight fraud — stream first, batch reconcile.

Design Dropbox

ADV

A syncing filesystem illusion: chunked content-addressed blobs, a metadata store for the tree, and clients that sync deltas.

Design Ticketmaster

ADV

A flash-sale inventory problem: waiting rooms, fair-ish queues, atomic seat holds, and payments — hot keys and correctness over cute microservices.

Design Uber matching

ADV

Riders request, drivers stream location, a matcher pairs them with geo indexes, then a trip lifecycle and pricing — realtime plus inventory of cars.

Design Zoom-like video calls

ADV

Realtime media: signaling, media servers (SFU), NAT traversal, and a hard latency budget — the tougher cousin of chat.
