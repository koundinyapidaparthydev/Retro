Design Pastebin / file share

CORE

The problem they give you

They will not say “Design Pastebin / file share.” They describe this:

Given: Engineers want to dump a log or a 40 MB file and send a link.

Find: v1: upload, get an unguessable URL, download. Bytes and metadata are different stores.

Tiny example: 10M creates/day, 50 KB average, one gist goes viral at 20k download QPS.

Name of the tool

Upload text or a file, get a link, download or view — object storage for bytes, metadata in a DB, optional expiry and privacy.

Why this tool

This is URL shortener plus blobs.

Approach

  1. Mint unguessable id; insert metadata; presign PUT; client uploads; complete marks ready.
  2. Read: authz → CDN/signed GET or small-text cache.
  3. TTL lifecycle on the bucket and a DB sweeper.

You say this first

I'd treat this as a 45-minute HLD. First I lock v1 of Pastebin / file share: who uses it, read vs write, latency, what is v2. Upload text or a file, get a link, download or view — object storage for bytes, metadata in a DB, optional expiry and privacy.

Then API, data, one write path and one read path. Deep dive: Mint unguessable id; insert metadata; presign PUT; client uploads; complete marks ready.. Text in DB vs always S3: simple queries vs one path for all sizes.

More notes if you want them

This is URL shortener plus blobs. It teaches 'metadata vs bytes,' presigned upload, and public vs private links. It is the on-ramp to Dropbox.

Use when: Gist-like products, ephemeral file drop, interview follow-on to URL shortener.

Skip when: Do not put 50 MB pastes in Postgres TEXT.

Trap: XSS from rendered HTML pastes — escape or sandbox.
