Authorization: RBAC and ABAC

NEXT

Definition

Role-based vs attribute-based access control — how you decide what an authenticated principal is allowed to do.

Why it exists

Authentication is who; authorization is what.

Approach

  1. Authenticate first; then authorize action + resource, not just 'is logged in.'
  2. Start RBAC for coarse roles; add resource ACLs or ReBAC for sharing.
  3. Always filter by tenant in the data layer, not only in the UI.

You say this first

Role-based vs attribute-based access control — how you decide what an authenticated principal is allowed to do. I'd only add it if a requirement we wrote down actually needs it. RBAC: internal tools, simple SaaS roles, service accounts.

Tradeoff: RBAC: simple ops, coarse and explodes under edge cases.. Failure mode: IDOR: authorize only the route, not the object id. On multi-tenant designs, say 'tenant_id in the PK or RLS' before you say Kubernetes.
