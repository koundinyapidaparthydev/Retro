The problem they give you

They will not say “Blue-green, canary, and rolling deploys.” They describe this:

Given: The last “big bang” deploy took checkout down globally for 12 minutes.

Find: Pick rolling, canary, or blue-green for this change, and how you abort.

Tiny example: 200 instances, a bad migration, 1% of users see errors for 8 minutes before anyone notices.

Name of the tool

How you ship new bits without a big-bang outage — two environments, a small slice of traffic, or instance-by-instance replacement.

Why this tool

Change is the top reliability killer.

Approach

  1. Expand/contract schema: add columns nullable first, dual-write if needed, then switch reads.
  2. Keep N and N-1 API compatibility during the roll.
  3. Split traffic; watch error budget and key business KPIs; abort automatically.

You say this first

How you ship new bits without a big-bang outage — two environments, a small slice of traffic, or instance-by-instance replacement. I'd only add it if a requirement we wrote down actually needs it. Rolling: default for stateless services on Kubernetes.

Tradeoff: Rolling: cheap, mixed versions for longer.. Failure mode: Breaking API in the same release as the last old client. Mention expand/contract when you add a field to the user table.

More notes if you want them

Change is the top reliability killer. Your HLD should include a deploy story: migrations, compatible APIs, and how you halt a bad release before 100% of users eat it.

Use when: Rolling: default for stateless services on Kubernetes.

Skip when: Do not blue-green a stateful primary without a data plan — you will split writes.

Trap: Breaking API in the same release as the last old client.
