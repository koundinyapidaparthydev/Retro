Service mesh (concept)

ADV

The problem they give you

They will not say “Service mesh (concept).” They describe this:

Given: Every language reimplemented retries, mTLS, and timeouts differently. Outages look like “the client library.”

Find: Decide whether a mesh is worth the ops tax, or a gateway + libraries is enough.

Tiny example: 35 services, 4 languages, you do not have a platform team of 12.

Name of the tool

Sidecars or a shared proxy layer that give you mTLS, retries, discovery, and telemetry without rewriting every app.

Why this tool

Meshes show up when the interviewer asks how 80 services get consistent timeouts and identity.

Approach

  1. Deploy proxies; issue workload identities; default deny + allow by identity.
  2. Set timeouts, retries (idempotent only), and outlier ejection as mesh policy.
  3. Export golden metrics from the proxy so every service has RED without custom code.

Tradeoff: Uniform security/telemetry vs platform cost and latency.. Failure mode: Retry storms from mesh + app + LB all retrying. Describe mesh in two sentences, then say you would not start there for a URL shortener.

More notes if you want them

Meshes show up when the interviewer asks how 80 services get consistent timeouts and identity. You should explain the data plane vs control plane and not promise a mesh as a substitute for good APIs.

Use when: Many services, many languages, need for mTLS and uniform telemetry.

Skip when: A modular monolith or three services — start with a library and a gateway.
