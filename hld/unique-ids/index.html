Unique IDs: UUID, Snowflake, and ticket servers

CORE

The problem they give you

They will not say “Unique IDs: UUID, Snowflake, and ticket servers.” They describe this:

Given: Ids are minted on 40 boxes. Some must sort by time; none may collide; some must not be guessable.

Find: Pick UUID, Snowflake, or a ticket server for this write — and name the failure.

Tiny example: 80k ids/s, two regions, NTP is 400ms off on one host.

Name of the tool

How you mint unique, sometimes sortable IDs without a single global auto-increment bottleneck.

Why this tool

URL shorteners, tweets, and chat messages all need IDs.

Approach

  1. If you have one primary and low write rate, sequences are fine.
  2. If many writers, use UUID v7 or Snowflake with assigned worker ids.
  3. Keep a sequence per worker; block if the clock jumps backward.

You say this first

How you mint unique, sometimes sortable IDs without a single global auto-increment bottleneck. I'd only add it if a requirement we wrote down actually needs it. Snowflake/ULID: feeds, chat, URL ids, anywhere you sort by time roughly.

Tradeoff: Random UUID: no coord, worse locality and sort.. Failure mode: Two workers with the same worker id after a bad deploy. For URL shortener and Twitter, propose Snowflake or a range allocator; mention clock skew.

More notes if you want them

URL shorteners, tweets, and chat messages all need IDs. Database auto-increment does not survive multiple primaries. UUID v4 does not sort by time. Snowflake-style IDs are the interview classic — including clock and uniqueness pitfalls.

Use when: Snowflake/ULID: feeds, chat, URL ids, anywhere you sort by time roughly.

Skip when: Do not use a global Redis INCR as the only ID gen without HA and persistence thought.

Trap: Two workers with the same worker id after a bad deploy.
