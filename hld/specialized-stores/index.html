The problem they give you

They will not say “Time-series, graph, and columnar stores.” They describe this:

Given: Metrics, a friend graph, and a finance warehouse are all being forced into one Postgres.

Find: Pick time-series, graph, or columnar only when the access pattern is that shape.

Tiny example: Metrics 2M writes/s, 4-hop “friends of friends,” year-long SUM by region.

Name of the tool

Engines built for append-only metrics, multi-hop relationships, and analytic scans — when a row store is the wrong shape.

Why this tool

Presence heartbeats, friend-of-friend, and warehouse scans each punish Postgres in different ways.

Approach

  1. Metrics/heartbeats → TSDB or a metrics pipeline, not rows per beat in OLTP.
  2. Multi-hop social/authz → edge tables or a graph service with caching.
  3. Wide analytics → columnar warehouse/lakehouse fed by CDC/batch.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Is this still a relational table?
  • When do you bring in TSDB / graph / column store?
  • You queried a graph like a join of six tables.

You say this first

Engines built for append-only metrics, multi-hop relationships, and analytic scans — when a row store is the wrong shape. I'd only add it if a requirement we wrote down actually needs it. TSDB: SLI metrics, device telemetry, trading ticks.

Tradeoff: Specialized speed vs another operational system and sync.. Failure mode: High-cardinality labels in a TSDB (user_id on every metric). For metrics pipeline and ads, say columnar/OLAP; for presence, TS or in-memory; for friends, edge tables.

More notes if you want them

Presence heartbeats, friend-of-friend, and warehouse scans each punish Postgres in different ways. Naming a TSDB, graph DB, or column store shows you match the access pattern. Using all three on a TODO app shows you do not.

Use when: TSDB: SLI metrics, device telemetry, trading ticks.

Skip when: Do not put checkout rows in ClickHouse as the only copy.

Trap: High-cardinality labels in a TSDB (user_id on every metric).
