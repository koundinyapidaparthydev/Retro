Block vs file vs object storage

CORE

The problem they give you

They will not say “Block vs file vs object storage.” They describe this:

Given: A database wants a disk, a laptop wants a filesystem, and a video wants a bucket.

Find: Pick block vs file vs object for each blob of data on the board.

Tiny example: Postgres data dir, NFS home dirs, 4K video renditions, 50 TB/year growth.

Name of the tool

Three ways to persist bytes: disks you mount, filesystems you share, and HTTP objects you address by key. They are not interchangeable.

Why this tool

Dropbox, video, and databases all 'store files' but want different primitives.

Approach

  1. Databases and logs → block (local SSD/EBS) in the region's AZs.
  2. Shared POSIX apps or home dirs → file store, with eyes open on scale.
  3. User-generated bytes and artifacts → object + metadata DB + CDN.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Where do these bytes live — EBS, NFS, or S3?
  • Can the app treat S3 like a disk?
  • Random 4 KB writes vs a 2 GB immutable object.

You say this first

Three ways to persist bytes: disks you mount, filesystems you share, and HTTP objects you address by key. They are not interchangeable. I'd only add it if a requirement we wrote down actually needs it. Block: stateful data stores, boot volumes.

Tradeoff: Block: fast and familiar, attached to a node, pricier at lake scale.. Failure mode: Single-AZ block volume for a 'HA' database. For Dropbox/YouTube, say object for bytes, SQL for metadata, block only under the databases.

More notes if you want them

Dropbox, video, and databases all 'store files' but want different primitives. Putting a database on object storage without a designed FS, or putting a billion photos on NFS, are classic HLD mistakes.

Use when: Block: stateful data stores, boot volumes.

Skip when: Do not put the only copy of Postgres on a network filesystem you do not understand.

Trap: Single-AZ block volume for a 'HA' database.
