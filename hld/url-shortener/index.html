Design a URL shortener

CORE
AmazonhotGoogleoftenMetaoftenMicrosoftoftenThe standard first HLD.

The problem they give you

They will not say “Design a URL shortener.” They describe this:

Given: People need to paste long links into SMS and tweets.

Find: v1: mint a unique short code and redirect fast. Custom aliases and full analytics are later.

Tiny example: Hundreds of writes/s, 50k redirect QPS. A viral code must not melt the primary.

Name of the tool

Turn a long link into a short code, save the pair, and when someone opens the short link, send them to the long one — fast, with a cache.

Why this tool

This problem teaches the 7-step method in miniature: tiny write path, huge read path, ID generation, and a cache.

Approach

  1. Generate unique code (Snowflake → base62) with a collision retry; persist; return short URL.
  2. Redirect path: Redis get → else DB → fill cache → 302.
  3. Expire via TTL job or lazy check of expires_at.

Whiteboard prompts

These are problem statements. The algorithm name is your answer, not the title of the question.

  • Design bit.ly.
  • 301 or 302 — and why stats break.
  • Someone scrapes sequential codes.

You say this first

v1 is mint a unique code and 302 fast. Redirects dwarf writes. POST /urls mints Snowflake→base62, writes SQL. GET /{code} hits Redis, then SQL, then 302. Analytics stay off the read path.

Offer 301 vs 302, custom aliases as a CP write, bloom for missing codes, and why the table is not only Redis if links must survive a flush.
