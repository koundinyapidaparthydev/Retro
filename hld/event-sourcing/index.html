ADV

The problem they give you

They will not say “Event sourcing.” They describe this:

Given: Support needs “show me every change to this order,” not just the latest row.

Find: Decide whether the log is the source of truth — or you just need an audit table.

Tiny example: Order state machine, 5k transitions/s, a bug shipped and you must rebuild projections.

Name of the tool

The write-side source of truth is an append-only log of facts; current state is a fold over those events. Powerful, easy to overuse.

Why this tool

Ledgers, collaborative editing, and audit-heavy domains sometimes want the history as the data.

Approach

  1. One stream per aggregate (account_id); append with expected version.
  2. Snapshot every N events; load snapshot + tail to serve commands.
  3. Project to read models asynchronously; rebuild when projections change.

You say this first

The write-side source of truth is an append-only log of facts; current state is a fold over those events. Powerful, easy to overuse. I'd only add it if a requirement we wrote down actually needs it. Wallets, booking histories, collaborative documents, workflows you must replay.

Tradeoff: Perfect history and projections vs complexity and PII headaches.. Failure mode: Mutable 'events' — then it is not a log. For payments/wallet, you can event-source the ledger and still use SQL rows as the snapshot.

More notes if you want them

Ledgers, collaborative editing, and audit-heavy domains sometimes want the history as the data. Event sourcing is not 'we have Kafka.' It is a persistence choice with replay, versioning, and snapshotting. Interviews reward using it only where history is the product.

Use when: Wallets, booking histories, collaborative documents, workflows you must replay.

Skip when: Simple CRUD profiles and CMS pages.

Trap: Mutable 'events' — then it is not a log.
