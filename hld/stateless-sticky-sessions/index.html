HLD/Architecture

Stateless services and sticky sessions

CORE

Definition

Keep request-handling boxes disposable. If you need affinity, know why — and what you will do when that box dies.

Why it exists

Horizontal scale only works if any replica can handle the next request.

Approach

  1. Move session and CSRF tokens to a shared store; keep apps empty.
  2. Store uploads and exports in object storage, not /tmp on one pod.
  3. For WS, accept stickiness of the socket plus a bus for cross-instance fan-out.

Keep request-handling boxes disposable. If you need affinity, know why — and what you will do when that box dies. I'd only add it if a requirement we wrote down actually needs it. Stateless: almost all HTTP APIs and workers.

Tradeoff: Shared session store: extra hop, you can drain and scale.. Failure mode: Local disk as the source of truth. Say 'stateless app + Redis session + S3 files' as the default three-liner.

More notes if you want them

Horizontal scale only works if any replica can handle the next request. Sticky sessions paper over in-memory user state and then fail at deploy time. Interviews want Redis (or a JWT) for sessions and a clear exception list (WS, upload chunks).

Use when: Stateless: almost all HTTP APIs and workers.

Skip when: Do not scale a sticky-session monolith to 50 nodes and call it cloud-native.

Trap: Local disk as the source of truth.
