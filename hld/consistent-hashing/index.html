The problem they give you

They will not say “Consistent hashing and virtual nodes.” They describe this:

Given: You added four cache nodes and suddenly 80% of keys missed. The DB lit up.

Find: Place keys so adding or losing a node moves only a slice, not the world.

Tiny example: 32 cache nodes, one dies, virtual nodes uneven, a hot key still pins one box.

Name of the tool

Put servers and keys on a ring. A key belongs to the next server clockwise. Add a server and only nearby keys move — not everything.

Why this tool

This is a named HLD algorithm, like Raft.

Approach

  1. Hash keys and node vnodes onto a ring; store N replicas along the ring with AZ diversity.
  2. On join/leave, stream only the affected key ranges.
  3. Keep a membership version so clients do not write the wrong owner forever.

You say this first

A ring that moves only a fraction of keys when nodes appear or die — the standard way to place cache and KV partitions. I'd only add it if a requirement we wrote down actually needs it. Distributed caches, Dynamo-style KV, partition placement.

Tradeoff: More vnodes: smoother load, heavier membership and more small ranges to move.. Failure mode: No vnodes → one node owns half the ring by unlucky hashes. Draw 4 nodes, add a 5th, shade the moved arc — that picture is the point.

More notes if you want them

This is a named HLD algorithm, like Raft. You should draw the ring, explain vnodes, and say what happens on a node death (remap, rebalance, and the herd on the neighbors).

Use when: Distributed caches, Dynamo-style KV, partition placement.

Skip when: Small, stable N where a directory or range map is simpler.

Trap: No vnodes → one node owns half the ring by unlucky hashes.
